# ブラウザ実装の不正耐性(ハックされないか)の検証と代替案

作成: 2026-10-14

「HTML(ブラウザ)で実装してもハックされないか」を検証した結果と、難しい部分の代替案をまとめる。
ここでの「ハック」は、プレイヤー(または第三者)がゲームを不正に有利にする行為と、サーバーそのものへの攻撃の両方を指す。

---

## 1. 結論(先に)

1. **ブラウザ側(HTML / CSS / JS)は守れない。守るのはサーバーである。** 画面のコードはプレイヤーが全部読めて、書き換えられ、送受信を偽造できる。これは HTML に限らず、アプリ版でも本質は同じ(時間がかかるだけ)。
2. したがって設計原則は **「サーバーが唯一の真実を持ち、画面は表示と入力だけ」**。この原則は現状すでに守られている(答えはサーバーだけが持つ、判定はサーバー、所有・点数はサーバーのメモリ)。
3. **HTML のまま続けてよい。** 代替案(アプリ化、WebAssembly、サーバー側描画)はどれも「改ざんを遅らせる」効果しかなく、費用に見合わない(第5章)。
4. **唯一、技術だけでは防げないのが「自動解答(ボット)」。** 問題がプログラムで生成できる以上、プログラムで解ける。これはどの実装方式でも同じで、対策は「検知して価値を下げる」多層防御になる(第4章)。
5. **いますぐ直すべき穴が 4 つある**(第6章)。いずれもサーバー側の小さな修正で済む。

---

## 2. 前提: ブラウザで何ができてしまうか

プレイヤーは開発者ツールで次のことが自由にできる。これを前提に設計する。

| できること | 意味 |
|---|---|
| JS・HTML・CSS を読む、書き換える | 画面上の制限(ボタンの無効化、表示の隠し)は無意味。地図上の「攻撃できる拠点」の判定も表示用でしかない |
| WebSocket の送受信を見る、偽造する、再送する | サーバーに届くメッセージは「画面が送った」と信用できない。すべての判定をサーバーで行う |
| localStorage を読む | 復帰コードは本人が見られる(本人のものなので問題ないが、XSS があれば盗まれる) |
| 画面を自動操作する(スクリプト、拡張機能、RPA) | 人間が操作している保証はない |
| 複数のブラウザ・端末・回線を使う | 1 人が多数のプレイヤーを名乗れる |

## 4. 自動解答ボットへの対策(技術だけでは防げないもの)

### なぜ防げないか

- 問題は「プログラムで生成し、答えは計算で決まる」(`DESIGN.md` 8.6)。生成できるものは解ける。
- 画面を自動操作する手段(ブラウザ拡張、RPA、WebSocket を直接話すスクリプト)は止められない。
- アプリ化しても、通信を観察して再現すれば同じ。端末のアテステーション(後述)でも、正規端末上での自動操作は止められない。

### 対策の考え方: 「防ぐ」ではなく「割に合わなくする」+「検知して価値を無くす」

| 層 | 対策 | 効果 | フェーズ |
|---|---|---|---|
| 速度 | 解答の最短時間をサーバーで持つ(出題から 1 秒未満の解答は無効。レベルが上がるほど下限を上げる) | 単純ボットの効率を人間並みに落とす | 1(手順4) |
| 頻度 | 1 プレイヤーの時間あたり解答数・獲得点の上限 | 24 時間稼働の価値を抑える | 1 |
| 検知 | 正答率・解答間隔の分布・稼働時間・操作の規則性を記録し、人間離れしたプレイヤーに印を付ける | ランキングから除外し、人が確認 | 2 |
| 確認 | 異常があるときだけ、人間確認(画像ではなく「この拠点の名前を打つ」など、ゲーム内の軽い確認)を挟む | 常時の CAPTCHA は体験を壊すので、しきい値超過時だけ | 2 |
| 問題設計 | 入力式・図や表の読み取り・コマンド操作(帯 B 以降)は、4 択より自動化の手間が大きい | ボットの開発コストを上げる | 2〜3 |
| 価値設計 | 中立拠点の点数は低く、他プレイヤーとの攻防や高レベル帯の固定問題に価値を置く | ボットで稼げる部分の価値を下げる | 2〜 |
| 発想の転換 | 帯 C 以降(コマンド)では「自動化できること」自体が技能。自作スクリプトを許す「自動化枠」のランキングを別に設ける案 | 不正を正規の遊びに変える | 3〜(未決) |
| 規約 | 利用規約で自動操作と多重アカウントを禁止し、検知時はランキング除外・拠点の回収 | 対処の根拠 | 公開前 |

**到達点の目安**: 「ボットを作ることはできるが、作っても人間のトッププレイヤーに勝てず、検知されてランキングに載らない」状態。

## 5. 代替案の比較(HTML が難しい場合)

| 方式 | 改ざん耐性 | ボット耐性 | 費用・手間 | スマホ | 評価 |
|---|---|---|---|---|---|
| **HTML + サーバー権威(現状)** | 低(画面は読める)。ただしサーバー権威なら読めても勝てない | 低〜中(第4章の対策次第) | 小。ビルド不要、すぐ遊べる(企画の核) | 可 | **採用**。弱点は第4章と第6章で補う |
| JS の難読化・WebAssembly 化 | 低〜中(解析を遅らせるだけ) | 変わらない(通信を再現されれば同じ) | 小〜中 | 可 | 不採用。効果が薄く、デバッグが難しくなる |
| ネイティブアプリ(iOS/Android)+ 端末アテステーション | 中(改変アプリや root 端末を検知できる) | 中(正規端末での自動操作は残る) | 大。ストア審査、2 プラットフォーム、審査でハッキング表現の扱いに注意 | 可 | 将来の選択肢。HTML 版と併存させ、ランキングの「検証済み」枠に使う案 |
| Electron / WebView で包む | 低(中身は HTML と同じ) | 変わらない | 中 | 不可(PC のみ) | 不採用 |
| サーバー側描画(画面を動画で配信) | 高(画面にロジックが無い) | 中(画像認識で自動化は可能) | 非常に大。遅延、サーバー費用 | 可だが重い | 不採用 |
| 問題を画像で出す | 低(OCR で読める) | 低〜中 | 小 | 可 | 不採用。アクセシビリティも落ちる |

**結論**: HTML を続ける。「画面は信用しない」原則を守り、第4章・第6章の対策をサーバーに入れる。アプリ版は、人気が出てランキングの信頼性が事業価値になった段階で、検証済み枠として追加する。

## 8. 検証の仕方(自分でハックしてみる)

公開前に、次の「攻撃テスト」を自動テスト(`test/abuse.js` 案)として持つ。

1. 偽メッセージ: 未知の種別、型違い、巨大な値、未知のフィールドを送っても落ちない・反映されない
2. 他サイトからの接続: `Origin` を偽った接続が拒否される
3. 総当たり: 4 択を連続で外したとき、待ち時間が伸びること
4. 参加スパム: 同じ接続元から短時間に大量の `join` を送っても拠点が増えないこと
5. 連打: 秒間 100 メッセージで切断されること、他の接続に影響しないこと
6. 期限切れ: 制限時間後の解答が拒否されること(手順4 以降)
7. 配信の中身: スナップショットに答え・復帰コード・他人のトラップが含まれないこと(一部は `test/world.js` に実装済み)
8. 模擬ターミナル: OS コマンド・実 DNS・実 HTTP が一切呼ばれないこと(フェーズ3)
