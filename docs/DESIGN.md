## 1. 概要

| 項目 | 内容 |
|---|---|
| 日本語名称 | パケット陣取り |
| 英語名称 | Packet Conquest |
| ジャンル | ネットワーク学習 × オンライン陣取り対戦(ブラウザゲーム) |
| コンセプト | ネットワークの知識に正解するほど、自分のネットワークが世界中へ広がっていく |
| 対象 | ネットワークを学ぶ学生・社会人。資格試験(IT パスポート、基本情報技術者、CCNA、ネットワークスペシャリストなど)の学習者 |
| 動作環境 | ブラウザ(パソコン・スマホ)。サーバーは Azure App Service |

### 狙い

- **遊びと学習を一致させる**: 知識そのものが操作になる。問題に答える、コマンドを打つことが、そのまま攻撃・防御になる
- **長く遊ばれる(継続率)**: 制限時間のない永続ワールド、やりこみ要素、トラップによる攻防で、毎日戻ってくる理由を作る
- **将来の事業化・M&A を視野に入れる**: 買い手(教育会社、資格団体、セキュリティ企業など)が評価するのは、利用者数・継続率・収益の実績。大人がお金を払う分野(資格・企業研修)に直結させる

## 2. 現状: 試作版 v0.1(実装済み)

部屋コード制、4分間の対戦。**永続ワールドに作り替える前の検証用**。

### 実装済みの機能

- 部屋コードで最大6人(ボットを含む)が対戦。ホストが開始し、ボットを追加できる
- 日本とその周辺の簡略化した地図(15拠点、20リンク)。拠点の種類は DC(1点)・GW(海底ケーブルの陸揚げ拠点、2点)・IX(相互接続点、3点)
- 自分の拠点とつながった拠点を攻撃、自分の拠点を防御強化(Lv 最大3)。防御 Lv が高いほど問題が難しい(難易度1〜3)
- サブネット計算の4択問題を**プログラムで自動生成**(マスク、ネットワークアドレス、ブロードキャスト、ホスト数、同一ネットワーク判定)。答えは計算で求めるので常に正確。解答後に解説を表示
- 不正解で4秒間操作不可
- 切断後60秒以内なら同じプレイヤーとして再接続できる(合言葉はタブごとに sessionStorage へ保存)
- 路線図風の画面。自分の陣地が「路線」のように色でつながる。ライト・ダーク両対応、スマホでは地図が横スクロールし、開始時に自分の拠点を表示

### 技術構成

| 役割 | 使用技術 |
|---|---|
| サーバー | Node.js 20 以上、`http` + `ws`(WebSocket、パス `/ws`) |
| 画面 | HTML / CSS / JavaScript(Canvas で地図描画)。ビルド不要 |
| 状態 | サーバーのメモリ上(再起動で消える) |
| 配置 | Azure App Service(Linux、Node 20 LTS、B1 以上推奨) |

### ファイル構成

```
server/index.js            HTTP 配信 + WebSocket 中継、定期処理(1秒ごとの tick、25秒ごとの ping)
server/room.js             部屋・得点・攻撃/防御・ボット(フェーズ1で world.js に作り替える)
server/map/japan.js        地図データ(拠点・リンク・隣接表・開始地点)
server/questions/subnet.js 問題の自動生成(サブネット計算)
public/            画面(index.html, style.css, app.js)
test/check.js      問題3万問を計算し直して答えを検証
test/e2e.js        実サーバーに2人で接続し1試合を通す
```

### 既知の制約

- 状態がメモリにあるため、**インスタンスは1台**でしか動かない。再起動で世界が消える
- ログインなし。プレイヤーは部屋ごと・タブごとの一時的な存在
- Azure では WebSocket を有効にし、Always On を推奨(README 参照)

## 3. 確定した仕様(次の版で実現する)

### 3.1 永続ワールド

- **制限時間なし**。全世界のネットワークを、すべてのプレイヤーが一つの世界で取り合い続ける
- ゲームを始めると、**選んだ開始地域に自分専用のノードが新しく生まれ**、近くの地域拠点とつながる。そこから広げていく
- プレイヤーが増えるほど、世界のネットワークも大きくなる

### 3.2 難易度は10段階

| Lv | 内容 | 難易度 |
|---|---|---|
| 1 | 問題に解答(4択) | ★☆☆☆☆☆☆☆☆☆ |
| 2 | 時間制限つきで解答(4択、15秒) ※残すかは未決 | ★★☆☆☆☆☆☆☆☆ |
| 3 | 答えを入力して解答(選択肢なし) | ★★★☆☆☆☆☆☆☆ |
| 4 | 連続で正解(2問連続) | ★★★★☆☆☆☆☆☆ |
| 5 | 経路表(ルーティングテーブル)を読み、次の転送先を答える | ★★★★★☆☆☆☆☆ |
| 6 | トラップを見抜く(設定情報を読んでハニーポットか本物かを判定。罠を攻撃すると自分の拠点を1つ失う) | ★★★★★★☆☆☆☆ |
| 7 | コマンドで到達確認(`ping` / `tracert` を打ち、結果を読んで通れない場所を特定) | ★★★★★★★☆☆☆ |
| 8 | ファイアウォール突破(ACL を読んで抜け道を見つけ、通れるポート・送信元を指定するコマンドを入力) | ★★★★★★★★☆☆ |
| 9 | 経路を作って突破(`route add` などで迂回経路を設定) | ★★★★★★★★★☆ |
| 10 | 複合トラップを制限時間内に突破(ハニーポット + ファイアウォール + 経路遮断) | ★★★★★★★★★★ |

### 3.3 場面とレベルの対応

| 場面 | レベル |
|---|---|
| 開始地域の、誰のものでもないノード | 1〜3 |
| 他のプレイヤーの陣地 | 4〜6 |
| トラップが仕掛けられたノード | 7〜9 |
| 防御を固めきった地域の中心 IX | 10 |

守る側は、正解して得たポイントでハニーポット・ファイアウォールなどのトラップを自分のノードに仕掛けられる。オフライン中の守りがトラップの主な役割になる。

### 3.4 コマンド系(レベル7〜10)

- **制限時間あり**。目安: Lv7 90秒 / Lv8 120秒 / Lv9 150秒 / Lv10 180秒(数値は調整可)
- 時間切れは「逆探知された」扱い
  - 突破失敗。しばらくそのノードを攻撃できない
  - 守る側に「◯◯さんが侵入を試みました」と通知
  - Lv10 の失敗のみ、自分のノードを1つ失うなど重めのペナルティ
- **コマンドはすべて手で打ち込む。コマンドを選ぶボタンは作らない**(ユーザーの明確な方針: リアルに打ち込むことが、ハッカー感・ゲーム性・教育につながる)
- 本物のターミナルにある **Tab 補完**と **↑ キーの履歴呼び出し**は入れる方向(提案済み、ユーザーから異論なし。実装前に再確認するとよい)
- コマンドの書き方は、実務・資格試験で使う本物(`ping`, `tracert`/`traceroute`, `ipconfig`, `nslookup`, `route`, ACL の記法など)に合わせる
- コマンド系は**パソコン推奨**と画面で明示する。スマホは主にレベル1〜6と陣地の見張り用

### 3.5 安全面の方針(必ず守る)

- ターミナルは**ゲーム内の架空ネットワークだけで動く模擬環境**。実在のシステムには一切つながらない
- 地図やつながり方は実在を参考にしてよいが、**攻撃対象になる会社・機器は架空の名前**にする
- **実在サーバーのアドレスは載せない**
- 本物のシステムに使える攻撃手順は教えない。仕組みの理解と守り方の習得を重視する(学校・企業に導入してもらうためにも重要)

## 4. 未決事項(実装前にユーザーと決める)

1. 開始地域は自分で選ぶか、自動で割り当てるか
2. 個人戦か、陣営(チーム)制か(Ingress 型の陣営は初心者が入りやすい)

10. 拠点をすべて失ったときの再開方法(開始地域に再生成する案)
11. 終わりがない中での目標(週・月ごとのランキング、地域の支配率など)
12. ログイン方式

## 5. 技術方針(永続ワールド版)

| 課題 | 方針案 |
|---|---|

| 配置 | 引き続き Azure App Service |

## 6. 背景メモ(企画時の調査)

### 類似ゲームと差別化

- 最も近いのは **ThreatGEN: Red vs Blue**(Steam)。攻撃側・防御側に分かれてネットワークの支配権を奪い合うターン制の教育ゲーム。ただしクリック操作中心で、細かい技術は教えないと明記されている
- ほかに Hacknet(1人用ストーリー型)、hackmud / Grey Hack(娯楽寄りのハッキング MMO)、Bitburner(放置系)、TryHackMe / Hack The Box(ゲームではなく学習サービス)
- **差別化**: ブラウザですぐ遊べる・大人数・知識そのものが操作になる・コマンドを本物どおり手で打つ・日本語で日本の資格試験に直結。この組み合わせの既存ゲームは見つからなかった

### 参考にした成功例・失敗例

- Wordle(NYT が買収)、Agar.io(Miniclip)、Krunker.io(FRVR)、Kahoot!(投資ファンドが取得)など。共通点は、すぐ遊べる、ルールがすぐ分かる、自然に広まる、戻ってくる理由がある
- **Draw Something**(Zynga が買収後すぐに人気が落ちた)と **fly.pieter.com**(AI で数時間で作り一時は大きな売上、その後急減と報道)は、一時的な人気より継続率が大事だという教訓

### 8.5 フェーズ1の実装手順(案)

1. **拠点マスターと地図**(済 2026-10-12): `server/map/tokyo.js` に東京周辺29拠点のマスター(緯度・経度・種類・Lv・点数)。`server/map/geo.js` が描画座標への変換と、近い3拠点を結ぶリンクの自動生成を行う。検証は `test/map.js`。吉祥寺は遠すぎて中心が潰れるため外した。中心部が密なので、画面側にズームとパンが必要(手順6で対応)
2. **永続ワールド**(済 2026-10-12): `server/world.js`。部屋・4分タイマー・ボットを廃止し、世界は1つ。参加すると東京駅から 2.5 km 以内に自分専用の拠点が生まれ、近い2拠点とつながる。拠点マスターは起動時に store から読み、空なら `tokyo.js` でシード。手順3の復帰コード、手順7の初心者保護(24時間・3拠点以下)と全滅時の再生成(暫定)も最小限入れた。画面は緯度・経度から自分で投影。検証は `test/world.js`、E2E は `test/e2e.js`
3. **プレイヤーと復帰コード**: ニックネーム + 復帰コードで端末をまたいで同じプレイヤーに戻れる
4. **難易度 Lv1〜4**: Lv1 4択 / Lv2 15秒4択 / Lv3 入力式 / Lv4 2問連続。中立拠点は拠点マスターの Lv、他人の陣地は Lv4
5. **保存(Cosmos DB)**: `server/store.js`。起動時に読み込み、変更時に書き込む。手元はエミュレーターまたは保存なしで動く
6. **差分配信**: 接続時に全体、以後は変化分のみ。画面側も差分を受けて更新。(地図の拡大縮小・移動は 2026-10-12 に先行して実装済み)
7. **初心者保護・距離による防御上限・全滅時の再生成(暫定)**
8. **ランキングと支配率の表示**、画面の文言を永続ワールド向けに更新
9. **テスト**: 入力式の答えの判定、拠点マスターの検証(重複・座標範囲・Lv範囲)、E2E を永続ワールド向けに書き直す
10. **Azure**: Cosmos DB アカウント作成、接続文字列をアプリ設定へ、デプロイして確認


### 8.6 問題の供給方式(2026-10-12 ユーザー方針)

**場所ごとに問題が決まっている。** 供給の仕方はレベルで分ける。

| レベル | 供給方式 | 内容 |
|---|---|---|
| Lv1〜4 | その場で自動生成(現行方式) | サブネット計算など、計算で答えが決まる問題。拠点ごとの架空ネットワーク(10.x.0.0/16)を使って出題し、毎回変わる |
| Lv5〜10 | **固定問題を DB に保存** | 経路表・トラップ判定・コマンドシナリオなど。拠点ごとに用意し、**誰かがクリアしたら差し替える**。クリアされなくても**定期的に更新**する |

- 差し替えの理由: 答えの共有を防ぐ。クリアした人が答えを広めても、次の挑戦者には別の問題が出る
- 固定問題の作り方(案): 構造は固定のテンプレートにし、IP アドレスやポート番号などの値は生成時にランダムに決めて保存する。保存前に検証プログラムで答えを確認する。テンプレートは AI で下書きし人が確認(第5章の方針どおり)
- Cosmos DB に `questions` コンテナーを置く。項目: 拠点 id、レベル、本文(シナリオ)、答え(複数可)、解説、状態(active / cleared / expired)、作成日時、期限
- フェーズ1(Lv1〜4)では固定問題を使わないが、**問題の取得口を「生成」と「DB」の2系統に分けておき**、`questions` コンテナーの形だけ先に決める

未決(フェーズ2で決める): 拠点1つあたりの固定問題の本数、定期更新の間隔(週1など)、固定問題を拠点専用にするか共有プールに拠点の情報を差し込むか、検証の担当

### 8.7 拠点の登録(2026-10-12 ユーザー方針)

**拠点はどんどん追加できる。** Google マップに場所を登録するように、将来は利用者や事業者が拠点を登録できるようにする。登録された拠点も占領されれば誰かの支配下になる。

- **登録機能そのものはまだ先**。ただし、その仕組みと DB 設計はフェーズ1のうちに用意する
- 設計への影響
  - 拠点マスターはコードのファイルではなく **DB(Cosmos DB の `nodes` コンテナー)に持つ**。`server/map/tokyo.js` は初期データ(シード)として DB に流し込む役に変える
  - 拠点の項目: id(自動生成)、名称、種類、緯度・経度、Lv、点数、状態(公開 / 審査中 / 非公開)、登録者、登録日時、架空ネットワーク(自動で割り当て)、所有者(占領者)、防御 Lv、トラップ
  - 「登録者」と「所有者(占領者)」は別の項目。登録した人が守りやすいわけではない
  - **リンクは座標から自動生成**(すでにこの方式)。拠点が増えても地図が壊れない。近い拠点とつなぐ処理は、DB から読み込んだあとにサーバーで行う
  - **描画座標は画面側で計算**する。サーバーは緯度・経度を送り、画面がズーム・パンに合わせて投影する(拠点が増えて範囲が広がっても作り直しが要らない)
  - Cosmos DB の地理空間クエリ(位置と距離)を使えるよう、位置は GeoJSON の Point で保存する
  - 登録時の審査(不適切な名称、実在の攻撃対象になりうる施設の除外、重複)が必要。3.5 の安全方針に沿う審査基準は登録機能を作る時に決める
- 未決(登録機能を作る時に決める): 誰が登録できるか(ログイン必須か)、審査を人が行うか自動か、登録した拠点の Lv と点数の決め方、登録数の上限、営利利用(事業者が自社の拠点を出す)の扱い

拠点マスターのファイル(2026-10-14): `server/map/data/<region>.json`。項目は id(英小文字・数字・ハイフン)、name、kind、area(区・市)、lat、lon、level(1〜3)、value(1〜5)、tags(任意)。`server/map/load.js` が起動時に検証し、おかしければ止まる。DB 化したらこのファイルがシードになり、登録機能はこの項目に status / registeredBy / owner などを足したものを DB に書く。画面上の拠点の形は難易度で変える(Lv1 円、Lv2 角丸四角、Lv3 六角形、5点の拠点は星、プレイヤーの拠点は小さい円)

8.5 の手順への反映: 手順1の `tokyo.js` はシードデータに役割を変える。手順5(保存)で `nodes` に拠点マスターと状態を一体で保存し、起動時に DB から読む。手順6の画面側で緯度・経度から投影する

### 8.8 レベル体系と拠点の形(2026-10-14 ユーザー方針)

- 拠点のレベルは **1〜999**。1〜10 が基本で、**国はレベル 10**。11 以上は将来の拡張用に形だけ先に用意する
- 画面に最初に出るのは自分の見えている範囲。**東京の拠点は Lv1〜5**(都道府県・地方・国はその上のレベル)
- **原則(2026-10-14 決定)**: 難易度が上がるほど巨大組織・重要拠点なので大きくしてよいが、**模様は必ず変える(重複禁止)**。`test/shapes.js` で Lv1〜999 がすべて異なる模様であることを検証する

| Lv | 形 | 問題(設計書 3.2) |
|---|---|---|
| 1 | 円 | 4択 |
| 2 | 角丸四角 | 15秒4択 |
| 3 | 三角形 | 入力式 |
| 4 | ひし形 | 4 択(VLSM・ワイルドカード。2 問連続は廃止 8.18) |

### 8.9 拠点の形の拡張案(2026-10-14 ブレスト。10 の位の黒塗りと 100 の位の外枠は 8.8 に採用済み。特殊形は未決)

形は「層を重ねる文法」として作る。各層が独立しているので、桁や属性を増やしても同じ仕組みで描ける。

| 層 | 役割 | 候補 |
|---|---|---|
| 本体の形 | 1 の位 | 円、角丸四角、三角形、ひし形、五角形、六角形、星5、星6、星8、二重の星(いま実装済み) |
| 塗り | 10 の位の上半分(5〜9)など | 白抜き / 黒塗り(実際は所有者の色で塗る。中立は黒、ダークテーマは白) |
| 外輪 | 10 の位 | 0〜4 本。二重線を何本も重ねる |
| 外枠の種類 | 100 の位 | ギザギザ(歯車)、波線、点線、二重線、太線、およびその組み合わせ。外輪の間にギザギザを挟むのも可 |
| 特殊形 | レベルとは別の属性 | ハートなど 3 種ほど。イベント拠点・登録者の特別な拠点・季節限定などに使う案 |
| 札 | 補助 | Lv 番号。小さく描くときの保険 |

- 上限は 999 に広げた(拠点マスターの検証も 999 まで)
- 一覧ページには 100〜999 は百の位ごとに見本を数個ずつ載せる
- 決めること: 特殊形(ハートなど)を何に使うか、外輪の間にギザギザを挟むような追加の層を使うか

### 8.10 レベル分けの定義(2026-10-14)

レベル 1〜999 を操作方式の帯に分けた。帯の定義と、分野別の題材一覧は **`docs/LEVELS.md`** にある(たたき台。未決事項は同ファイルの第3章)。

2026-10-14 追記: Lv701〜999 を複数拠点の攻略パズル(拠点間の依存・時間窓・資源予算)と伝説級(観測推論・動く世界・同時多発・多段の総合戦)に強化。全題材に自動生成の方式(計算生成 / テンプレート+乱数 / シナリオ生成器 / 固定)を付け、2.11 に生成器と検証器の共通部品、第4章にゲームへ実装が必要な 27 の仕組みと作る順番を記載。LEVELS.md 第3章の未決 #8〜#14(帯 H/I の拠点の置き場、8.8 との食い違い、8.6 の供給方式の読み替えなど)はユーザーと決める。

### 8.11 ブラウザ実装の不正耐性(2026-10-14)

「HTML で実装してもハックされないか」の検証結果と代替案は **`docs/SECURITY.md`**。
結論: 画面(HTML/JS)は守れないので、サーバーが唯一の真実を持つ原則で続ける(現状その原則は守られている)。代替案(難読化、アプリ化、サーバー側描画)は改ざんを遅らせるだけで、HTML を続ける。
技術だけでは防げないのは自動解答ボットで、速度の下限・頻度の上限・異常検知・問題設計・価値設計の多層で割に合わなくする。
いますぐ直す穴: WebSocket の Origin 未検査、参加スパムで拠点が無制限に増える、メッセージの検査とレート制限が無い、4 択の総当たりが 16 秒で必ず通る(SECURITY.md 第6章 F1〜F6)。

### 8.12 突破回数と難易度(2026-10-17 ユーザー決定)

- **突破に必要な正解は常に 1 回。** 難しさは出題レベルだけで決める。回数で難しくすると、高レベル帯の固定問題(8.6)が何度も消費されて尽きるため。レベル分け(8.8 / LEVELS.md)はこのために作った
- 中立拠点の出題レベル = 拠点マスターの level。**防御強化は回数ではなく出題レベルを +1 する**(最大 3 段)。奪取されると強化は 0 に戻る
- 他プレイヤーの陣地は「拠点レベル + 強化」と 4 の大きい方(3.3)
- 実装: `world.js` の `levelFor` と `apply`(2026-10-17)。試作版の「防御 Lv を削ってから奪う」方式は廃止

### 8.13 出題の引き直し(2026-10-17 ユーザー決定)

- **拠点を選ぶたびに問題が変わるのは、ランダムに生成できる問題(Lv1〜4)だけ。** 高難易度の固定問題で毎回作り直すと、長いシナリオが一生終わらない
- Lv5 以上の固定問題は **拠点(×レベル)に紐づき、誰かがクリアするか定期更新されるまで同じ問題が残る**(8.6)。プレイヤーごとの途中経過(多段シナリオの進み具合)は保存し、離れて戻っても続きから
- 生成問題でも、同じ拠点を続けて選んだ場合は出題中の問題をそのまま返す(クリックで引き直せない)。別の拠点を選ぶと破棄される
- 実装: `world.ask` は出題中の問題を `pending.payload` に持ち、同じ拠点・同じモード・同じレベルなら再送する(2026-10-17)。固定問題の保持はフェーズ2(LEVELS.md 第4章 #11・#19)

### 8.14 地域マスター(2026-10-17。同日、宇宙まで含む世界共通の階層に変更)

Cosmos DB 格納用の地域マスターを `server/map/data/regions.json` に作った(まず東京)。**世界でも同じ基準で使う**ため、日本固有の種類ではなく段(tier)で表す。将来のために最上位は**宇宙**とし、地球以外の天体(月・火星・軌道上の施設)も同じ階層に置けるようにした(いまは実装しない)。

- 階層: **宇宙(tier 0)→ 天体(1。地球・月・火星・軌道上の施設)→ 大陸・広域(2)→ 国(3)→ 地方(4。無い国は省略可)→ 都道府県・州・省(5)→ 市・区・郡(6。拠点が属する最下層)→ 地区(7。必要な都市だけ)**。親は必ず自分より浅い段ならよく、段を飛ばせる(例: シンガポールは 国 → 市)
- いまの中身: universe → earth → asia → japan(JP)→ kanto → tokyo(JP-13)→ 23 区 + 8 市(kind は city、localKind に「区」「市」)。1 行 = Cosmos DB の `regions` コンテナーの 1 ドキュメント。項目は id、name、nameEn、kind、parent、code(ISO 3166 の国コード・地域コード)、status、nodeFile(拠点ファイルを持つ地域)、localKind(その国での呼び名)
- 拠点(`tokyo.json`)は `region` で最下層(leafKinds: city / district)の id を指す。`area` は表示用の名前で、`region` の名前と一致することを検証する
- 読み込み(`server/map/load.js`)で階層を検証し(親の存在、親が浅い段であること、世界が 1 つ、重複)、`regionDocs(nodes)` が保存用の形を作る。派生値として tier、country(属する国)、path(宇宙からの経路)、depth、center、bbox、nodeCount、levels(レベル分布)を各階層に集計して付ける
- `level`(地域そのものを拠点として出すときのレベル)は未決(LEVELS.md #1)のため null
- Cosmos DB のコンテナー案: `regions`(パーティションキー `/parent`)、`nodes`(`/region`)、`players`(`/id`)、`questions`(`/nodeId`)。地域を足すときは regions.json に 1 行追加し、拠点ファイルを `nodeFile` で結ぶ

### 8.15 拠点の名前は名所に限る(2026-10-17 ユーザー方針)

拠点の名前は地名ではなく**正しい名所の名前**(駅、公園、塔、寺社、競技場 など)を使う。使ってよいジャンル・避けるジャンル・書き方は **`docs/PLACES.md`**。世界共通の基準で、拠点マスターに `genre` を必須にする。東京マスターの地名・架空名の拠点 44 件は同日に名所の名前へ置き換え済み(PLACES.md 第5章)。拠点マスターは `genre` 必須で、「丁目」と架空名の DC / IX は検証で弾く。

### 8.16 収益モデル: 実在の場所のスポンサー拠点(2026-10-17 ユーザー方針)

- **実在する場所は、その所有者(店・施設・企業)が拠点として買い取れる**ようにし、宣伝広告として収益化する。8.7 の登録機能はこのための入口でもある(自分のお店を地図に追加できる。実装は後)
- 粒度は **駅ぐらい**でよい。丁目まで入れると細かすぎる。無料の初期拠点(名所)は PLACES.md の基準で選び、駅程度の密度にとどめる。細かい場所はスポンサー拠点として追加される
- スポンサー拠点は、3.5 の「企業名を出さない」原則の **同意に基づく例外**。本人(権利者)の申し込みと審査を経たものだけ、店名・施設名・ロゴ・リンクを出せる。無断で実在企業の名前を出すことは引き続きしない
- 広告であることを画面に明示する(景品表示法・ステマ規制への配慮)。ゲーム内で「攻撃される」表現がスポンサーの不利益にならないよう、スポンサー拠点の文言は「〇〇のネットワークに到達」など穏当にする(表現は要検討)
- 拠点の項目に足すもの(案): sponsorId、sponsorName、plan(枠の種類)、startAt / endAt(掲載期間)、link、logo、badge(広告表示)、billingStatus。regions / nodes のマスターとは別に `sponsors` コンテナーを持ち、nodes から参照する
- **決めること**: (1) 買い取りの意味。掲載権(広告枠)だけか、ゲーム内の初期所有権や特典(防御の強化、専用の問題)も付けるか。所有権まで売ると公平性が崩れるため、掲載権 + 見た目の特典を推奨 (2) 料金と期間の体系(月額 / 地域・レベル別) (3) 審査基準(PLACES.md 第3章の避けるジャンルは有料でも不可) (4) 一般ユーザーが自分のお店を追加する場合の無料枠と有料枠の線引き (5) スポンサー拠点のレベルと点数の決め方(高くすると目立つが、取り合いの中心になる)

**2026-10-17 決定(8.16 の未決への回答)**

1. **スポンサー拠点は乗っ取り不可。** プレイヤーはスポンサー拠点に**所属**でき、所属を選んだ人はそこからスタートできる(所属だけしてスタート位置は別、も可)。所属メンバーの活躍でスポンサー拠点の規模が大きくなる。新規の小さなお店でも最強のハックチームになりえる(→ 8.2 #2「個人戦」は、スポンサーへの所属という形のチーム要素を持つことになる。詳細はフェーズ2 以降で設計)
2. 収益化は当面「広告宣伝」程度の範囲と想定
3. **重要インフラは地図上に存在してよいがハック不可**(線がつながっていない)。寺社も同じ扱い(存在するがハック不可)
4. 購入形式でよい。金額で初期レベルが決まるなどの優遇はあってよい(先の話)
5. スポンサー拠点は取り合いの中心になってよい(拠点そのものは乗っ取れないが、その周辺と所属メンバーの陣地が攻防の中心になる)。スポンサー費用に応じて、**全マップ上に拠点を複数点在**できる(地域ごとに遊ぶ人が違うため宣伝になる)
6. 複合施設(六本木ヒルズ等): **許す**。名称を微妙に変えた表記: **許さない**(正式名のまま使う。それができないものは出さない)

実装への反映: 拠点に `hackable`(既定 true)を持たせ、false の拠点はリンクを張らず攻撃もできない(2026-10-17 実装。寺社に適用)。スポンサー拠点の所属・スタート・規模の仕組みはフェーズ2 以降。

### 8.17 駅の取り込み(2026-10-17 ユーザー決定)

- 東京都の **全事業者の全駅**(JR、東京メトロ、都営、私鉄、モノレール、新交通 など。約 750 駅)を拠点にする。手で選ばず、公開データから機械的に取り込む
- 出どころ: 国土交通省「国土数値情報 鉄道データ(N02)」2025 年度版(`N02-25_GML.zip`、全国、14.2 MB、GeoJSON 同梱)。配布ページ https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-N02-2025.html 。利用規約は政府標準利用規約 2.0(CC BY 4.0 互換、商用可)。**出典と加工の明記が必要**: 「「国土数値情報(鉄道データ)」(国土交通省)(配布ページ URL)を加工して作成」。画面(クレジット)と README に書く
- 駅データの属性: 鉄道区分(N02_001)、事業者種別(N02_002)、路線名(N02_003)、運営会社(N02_004)、駅名(N02_005)、駅コード(N02_005c)、グループコード(N02_005g。300 m 以内の同名駅を 1 グループ)。駅の形状は線なので、中点を拠点の位置にする
- 取り込み方: スクリプト(`tools/import-stations.js`)で、東京都の範囲(区・市の多角形は持たないので、都内の駅を都道府県名で絞れない場合は緯度経度の範囲 + 区・市の中心に最も近い地域へ割り当て)の駅を抽出し、グループコードで乗換駅を 1 つにまとめ、路線数・事業者数からレベルと点数を決める(案: 1 路線 Lv1、2〜3 路線 Lv2、4 路線以上または主要ターミナル Lv3〜4。東京・新宿・池袋・渋谷・品川・上野は手で Lv4〜5 に上書き)。手作りの名所(公園・寺社など)は残し、駅は取り込み結果で置き換える
- **島しょ部**: 駅がないので、建物や山の名称(例: 三原山、八丈富士、父島の二見港)を名所として手で入れる
- 区・市への割り当ては、拠点マスターの各区・市の中心(regions の center)に最も近いものを暫定とし、将来は行政区域データ(国土数値情報 N03)で正確にする

**取り込みの結果(2026-10-17)**: 東京都内の駅 651 件を取り込み(行政区域の多角形で都外を除外、300 m 以内の同名駅と 1.2 km 以内の同名グループを統合)。名所 64 件と合わせて 715 拠点。レベルは路線数から(1 路線 Lv1、2〜3 路線 Lv2、4 路線以上 Lv3)、主要ターミナルは手で Lv3〜5(大手町 5、東京・新宿・池袋・渋谷・品川・上野・霞ケ関 4 など)。架空ネットワークは 10.0.0.0/8 を /20 ずつ割り当て(4000 拠点まで)。駅と名所が 100 m ほど近接する組が 26 件あるが二重登録ではないので両方残す(検証は 25 m 未満だけ弾く)。
注意: それまで `.gitignore` の `data/` が `server/map/data/` にも効いていて、拠点マスターと地域マスターが Git に入っていなかった。`/data/`(ルートのみ)に直し、同日のコミットから含める。

### 8.18 Lv1〜10 の段階(2026-10-17 ユーザー決定: 2 問連続は使わない)

- **「2 問連続」は採用しない。** レベルは常に 1 問の難しさで表す(3.2 の旧 Lv4「2問連続」、LEVELS.md 帯 A の「2 問連続」は廃止)
- 難しさの上げ方は 3 つだけ: **問題の内容**(プレフィックスの位置、計算の段数、扱う概念)、**制限時間**、**解答方式**(4 択 → 入力)
- Lv1〜10 の段階(東京の拠点は 1〜5 を使う):

| Lv | 方式 | 1 問の内容 |
|---|---|---|
| 1 | 4 択 | 8 ビット区切り(/8, /16, /24)のマスク・ネットワークアドレス・ホスト数 |
| 2 | 4 択 | /25〜/28。ブロードキャスト、同じネットワークの判定が加わる |
| 3 | 4 択 | /19〜/23、/29、/30。区切りが第 3 オクテットや末尾にある計算 |
| 4 | 4 択 | 必要ホスト数から最小のプレフィックスを求める(VLSM)、ワイルドカードマスク |
| 5 | 4 択 | CIDR の集約(2〜4 個のネットワークをまとめる)、IPv6 の省略表記 |
| 6 | 4 択 + 15 秒 | Lv3 相当の内容 |
| 7 | 4 択 + 15 秒 | Lv5 相当の内容 |
| 8 | 入力式 | Lv3〜4 相当の内容を選択肢なしで入力 |
| 9 | 入力式 | Lv5 相当の内容を入力 |
| 10 | 入力式 + 60 秒 | Lv5 相当の内容。帯 B(Lv11〜)への橋渡し |

- 実装は手順 4。生成器(`server/questions/subnet.js`)に Lv4〜5 の種類(VLSM、ワイルドカード、集約、IPv6 省略)を足し、レベル → (内容, 制限時間, 方式) の対応を 1 か所の設定にする。答えの検証は `test/check.js` に追加する

**2026-10-17 訂正(8.18 を置き換える)**: **制限時間も難易度の道具にしない。** 2 問連続・制限時間といった小細工でレベルを変えない。レベルは **問われるネットワークの知識の難しさ** だけで決める。知識は 1〜999 を埋められるだけある(LEVELS.md 第 2 章の題材がその一覧)。解答のしかた(4 択 → 入力 → コマンド → 設定 → 構築)は難易度の道具ではなく、その知識を問うのに自然な形としてレベル帯ごとに決まる。

Lv1〜10 の段階(すべて 4 択。1 問の知識の難しさだけで上げる):

| Lv | 1 問の知識 |
|---|---|
| 1 | 8 ビット区切り(/8, /16, /24)のマスク・ネットワークアドレス・ホスト数 |
| 2 | /25〜/28 のネットワーク・ブロードキャスト・同じネットワークの判定 |
| 3 | /19〜/23、/29、/30(区切りが第 3 オクテットや末尾) |
| 4 | 必要ホスト数から最小のプレフィックスを求める(VLSM)、ワイルドカードマスク |
| 5 | CIDR の集約(2〜4 個をまとめる)、IPv6 の省略表記 |
| 6 | IPv6 のプレフィックスと範囲、リンクローカル、SLAAC の考え方 |
| 7 | 経路表(3〜4 行)の最長一致で次の転送先を選ぶ |
| 8 | ARP テーブル・MAC アドレステーブルから機器の場所を特定する |
| 9 | ACL(1〜2 行)を読んで通る・通らないを判定する |
| 10 | NAT/NAPT の変換表を読んで内外のアドレス対応を答える |

Lv11 以降は LEVELS.md 第 2 章の順(入力・読み解き → コマンド → 機器設定 → …)で、同じく知識の難しさだけで並べる。
制限時間は、高レベル帯の「逆探知」のような演出として使うかどうかを別途決める(難易度の段階づけには使わない)。

### 8.19 LEVELS.md の全面改訂(2026-10-17)

レベル 1〜999 を「操作方式の帯」から **「知識の領域(100 ごと)× 10 段」** に組み替えた(`docs/LEVELS.md` 第 1〜4 章)。原則は 8.18 の訂正版のとおり(知識の難しさだけ。制限時間・2 問連続・資源予算・情報を伏せることは難易度の道具にしない)。
