# 問題設計書: レベル 51〜100(アドレッシングと基礎の後半 〜 L2 の入口)

作成: 2026-10-18 / 対象: `docs/LEVELS.md` 第 4 章「1〜99 アドレッシングと基礎」の 51〜99 と、「100〜199 L2・L3 の動作」の最初の段(100〜109)の先頭 Lv100

この文書は **何を・どう生成し・どう検証するか** の設計書で、コードは含まない。題材の階段(LEVELS.md 第 4 章の段)は決定済みなので変えない。レベル 11〜50 は別の担当が同時に設計しており、本書は 51 以降だけを扱う。11〜50 と共通にすべき部品(入力欄・正規化・seed 付き乱数)は第 1 章にまとめ、11〜50 の設計書と突き合わせて 1 つに揃える前提で書く。

守ること(`CLAUDE.md`、LEVELS.md 第 1 章):
- 難しさは「問われる知識の難しさ」だけ。制限時間・2 問連続・情報の伏せ方は使わない
- 答えは正確でなければならない。計算で決まるものはプログラムで生成し、**別実装で解き直す検証テスト**を付ける
- 答えはサーバーだけが持つ(`q.meta`・`accept` はクライアントに送らない)
- アドレスは内側 `10/8`・`172.16/12`・`192.168/16`・`fd00::/8`・`fe80::/10`、外側は文書用 `192.0.2.0/24`・`198.51.100.0/24`・`203.0.113.0/24`・`2001:db8::/32` のみ。MAC は `02:` で始まるローカル管理アドレス。機器は架空メーカー「PC ネットワークス」(`devices.json`)の命名(R1、SW1、FW1、PC1)。ドメインは RFC 2606 の予約 TLD `.example` を使う(第 8 章の迷った点 9)
- ベンダー固有の名称には標準名を併記する(`terms.json`)。本書で出るのは AD 値(Cisco 社の用語「管理距離」。一般名は「経路の優先度」)だけ

## 1. 共通の仕様(51〜100 で初めて必要になるもの)

### 1.1 問題オブジェクトの拡張

現状(`basics.js`)は `{ text, options(4), answerIndex, explanation, table?, meta }` で、`world.answer` は `choice === pend.answerIndex` だけを判定する。51 以降は入力式が大半なので、`DB.md` 3.4 の `answerKind` に合わせて次を足す(LEVELS.md 第 6 章 #1・#2)。

| 項目 | 配信 | 内容 |
|---|---|---|
| `answerKind` | する | `choice`(4 択)/ `text`(入力) |
| `format` | する | 入力の種類。`number` / `ipv4` / `ipv4cidr` / `ipv6` / `ipv6cidr` / `addrport` / `ifname` / `devname` / `dnsname` / `aclverdict` / `token` / `prefixplan`。画面は placeholder と IME の初期状態(半角)を決めるのに使うだけ |
| `inputHint` | する | 入力欄の例示(「例: 10.0.1.0/24」)。答えそのものを示唆しない定型文に限る |
| `accept` | **しない** | 正規化済みの正解の配列。複数正解(Lv99 の計画問題)はここに並べるか、`verifier` を使う |
| `verifier` | **しない** | 正解との一致ではなく制約で判定する問題(Lv99)の判定器名と引数 |
| `defenseNote` | する(結果と一緒に) | 「守る側ならどうするか」の一文(第 6 章 #8。空は安全リンタで弾く) |
| `meta` | **しない** | 検証テストが使う真の値 |

`world.ask` の payload には `answerKind` / `format` / `inputHint` を足し、`world.answer` は `answerKind === 'text'` なら `normalize(format, 入力)` を `accept` と比較する(または `verifier` を呼ぶ)。不正解時の待ち時間倍増(F4)はそのまま。

### 1.2 入力欄の仕様(本書の範囲で入力式が初めて出るのは Lv52)

- 画面: 1 行のテキスト入力 1 つ。**Enter で送信**、送信ボタンも置く(スマートフォン用)。**Tab 補完なし、候補ボタンなし**(コマンド式ではないが「選ばせない」方針を揃える)。送信後は欄を無効化し、結果(正誤・正解・解説・defenseNote)を 4 択と同じ枠に出す。正解の表示は `accept[0]`(正規形)
- 空文字・空白のみは送らない。1 問につき送信は 1 回(`qid` で束ねる。再送は「この問題はもう終わっています」)
- 入力の長さは 200 文字まで。Lv99 の複数行は改行区切りで 1 つの文字列として送る(1,000 文字まで)
- 文字種の案内文を欄の下に固定で出す: 「半角で入力。IPv6 の省略形、先頭の 0、大文字小文字は自動でそろえます」

### 1.3 正規化の規則(サーバー側 `normalize(format, s)`。判定前に正解側にも同じ関数を通す)

共通: 前後の空白を除く → 全角英数字・全角記号(`．：／－`)を半角に → 連続する空白を 1 つに → 小文字化(機器名・IF 名・16 進)。

| format | 規則 | 受け付けない例(不正解扱いではなく「形式が違います」で再入力させず、そのまま不正解にする。理由: 再入力を許すと総当たりができる) |
|---|---|---|
| `number` | 桁区切り `,` と全角数字を除去して整数に。先頭 `+` は無視 | 小数、単位付き(「秒」「個」) |
| `ipv4` | 4 オクテット、各 0〜255、**各オクテットの先頭 0 は除く**(`010.000.001.001` → `10.0.1.1`) | 3 オクテット、256 以上 |
| `ipv4cidr` | `ipv4` + `/` + 0〜32。`10.0.1.0 255.255.255.0` の形も受け付けてプレフィックス長に変換。アドレス部はネットワークアドレスに切り詰めない(入力と正解を同じ規則で比べるので、`10.0.1.5/24` は不正解) | `/` のみ、マスクが連続 1 でない |
| `ipv6` | `::` を展開して 8 グループに → RFC 5952 の正規形(最長ゼロ連続 1 か所を `::`、同長なら先頭、先頭ゼロ省略、小文字)。既存 `basics.v6Canonical` を使う | `::` が 2 か所、グループ 9 個以上、`[]` 付き |
| `ipv6cidr` | `ipv6` + `/` + 0〜128 | |
| `addrport` | `ipv4` + `:` + 1〜65535(IPv4 のみ。本書の範囲で IPv6 の addr:port は出ない) | ポート 0、`:` なし |
| `ifname` | `GigabitEthernet0/1` / `Gi0/1` / `gi 0/1` / `g0/1` を `gi0/1` に。`Null0` / `null 0` → `null0`。比較は小文字 | |
| `devname` | 表に書いた機器名(R1、SW1、PC2…)を小文字化し、ハイフン・空白を除いて比較(`pc-2` ≡ `pc2`) | |
| `dnsname` | 小文字化、末尾の `.` を除く。`in-addr.arpa` / `ip6.arpa` のラベルは全角 `.` も半角に | |
| `aclverdict` | 2 トークン `動作 行番号`。順不同(`10 permit` ≡ `permit 10`)。暗黙の拒否は `deny implicit`(`暗黙`・`暗黙の拒否`・`implicit` を `implicit` に、`許可`→`permit`、`拒否`→`deny`)。`deny` だけで行番号なしは不正解(行番号を問う知識なので) | |
| `token` | 語彙表 `vocab.json` で正規化(日本語の別名 → 英字トークン)。例: `全ポート`・`フラッディング`・`flood` → `flood`、`破棄`・`drop` → `drop`、`マスク`・`サブネットマスク` → `mask` | 語彙表に無い語 |
| `prefixplan` | 改行・`,`・`;` で分けた各行を `名前 ipv4cidr [ipv6cidr]` として読む。名前は `devname` 規則、順序は無視して**集合**として比較 | 行数が要件の拠点数と違う |

正規化そのものを `test/normalize.js` で網羅する(全角・先頭 0・`::` の展開・IF 名の別表記・aclverdict の順不同・token の別名。既知の入出力 50 組以上と、`normalize(normalize(x)) === normalize(x)` の冪等性をランダム 1 万件)。

### 1.4 seed 付き乱数と保存の形

- 既存 Lv1〜10 は `Math.random` だが、Lv11 以降は固定問題(DESIGN.md 3.5、DB.md 3.4)なので **`makeRng(seed)`**(mulberry32 など 32 ビットの決定的 PRNG)が返す `rand / pick / shuffle` を生成器に渡す。問題 = (`templateId`, `seed`, `generatorVersion`)
- 各生成器は `make(level, node, rng)` の形で、`templateId` を `q.templateId` に入れる(例: `napt-add-v1`)。版は生成器ファイルの定数 `VERSION = '2026.10'`
- 保存するスナップショットは `rendered`(text・table・options・answerKind・format・inputHint)と `answer`(index または accept / verifier)と `explanation` / `defenseNote`。クリアで seed を変えて差し替え
- 計算生成の問題はその場生成でも正確さは保てるが、8.13(拠点に紐づき、クリアまで同じ問題)に従うなら保存する。どこまで保存するかは迷った点 13

### 1.5 検証テストの流儀(`test/check.js` / `test/basics.js` と同じ)

- 生成器とは**別の実装**(素朴な総当たり・逐次シミュレーション・列挙)で答えを解き直し、`assert` で一致を確認する
- 4 択: 選択肢 4 つが重複しない、`answerIndex` が範囲内、誤答が正解と**値として**同じでない(表記違いの同値を含めて `normalize` 後に比較)
- 入力: `accept` の全要素が `normalize` の不動点(正規形)である。誤入力の代表(ありがちな間違い)が `accept` に**入らない**ことも確認する
- 件数: 計算生成は固定 seed 列で **1 万件/生成器**(CI の再現性のため seed は `i` から決める)。FactBank 由来のテンプレートは**全数**(表の全行 × 問いの型)。境界値は各段に明記する
- `text`・`explanation`・`defenseNote`・`table` の全文を**安全リンタ**(第 6 章 #7)に通す: 使えるアドレス範囲・`.example` 以外のドメイン禁止・`banned.json` の禁止語
- 全種類(`q.type`)が出ることを `seenTypes` で確認(既存と同じ)

### 1.6 用語

- **生成器**: パラメータと seed から**計算**で答えが決まる。別実装で再計算して検証
- **固定テンプレート**: 文章の型は固定で、差し込む値(サービス名・番号・メッセージ名)を FactBank(`facts.json`)から seed で選ぶ。答えは表の値。表は人が一度確認し、テストは表照合と誤答の非重複
- どちらも (templateId, seed, 版) で保存する点は同じ

## 2. 51〜60 トランスポートとポート

段の知識(LEVELS.md): TCP/UDP の違い、主要ポート、3 ウェイハンドシェイクのフラグと seq/ack、エフェメラルポート、5 タプル、NAPT 表に往路 1 行を**自分で足す**。前の段(41〜50 のカプセル化)に第 4 層の識別子を足し、接続単位で状態を追う。NAPT の復路・静的 NAT・ポートフォワードの両方向は 240〜249 に残す。

ゲーム内の規則として固定するもの(迷った点 1・12):
- エフェメラルポートの範囲は IANA の **49152〜65535**。誤答には 1024 未満と既定ポートだけを使い、OS 差のある範囲(32768〜49151)を選択肢に出さない
- NAPT の変換はポート保持(内側ポートをそのまま内側グローバルのポートに使う)。衝突したら**その番号から上へ順に探して最初の空き**を使う。TCP と UDP は別の名前空間
- 初期シーケンス番号(ISN)は 1,000,000〜2,000,000,000 の範囲で作り、2^32 の折り返しは出さない(迷った点 10)

### 2.2 例題

**Lv51**(4 択)
問: 次のうち、TCP にはあって UDP にはない性質はどれ？
選択肢: A. 届いたことの確認(ACK)と再送 / B. ポート番号で宛先のアプリケーションを区別する / C. チェックサムで誤りを検出する / D. ブロードキャスト宛に送れる
正答: A。解説: 確認応答・再送・順序の保証は TCP の性質。ポートとチェックサムは両方にあり、ブロードキャストは UDP だけ。守る側: 再送が無い UDP は到達の保証が無いので、監視では応答の有無を別に確認する。

**Lv52**(入力・number)
問: NTP(時刻同期)が既定で使う UDP ポート番号は？
正答: `123`。解説: NTP は UDP 123。DNS 53、DHCP 67/68、SNMP 161/162 も UDP が主。

**Lv55**(入力・number)
問: クライアントの初期シーケンス番号が 2,000,000、サーバーの初期シーケンス番号が 5,000,000 のとき、サーバーが返す SYN/ACK セグメントの ACK 番号は？
正答: `2000001`。解説: ACK 番号は「次に受け取りたいバイト」。SYN は 1 バイト分を消費するので、相手の ISN + 1 = 2,000,001。この SYN/ACK の seq は 5,000,000。

**Lv56**(入力・number)
問: ハンドシェイク後、送信側の seq 番号は 20,001 から始まる。1,460 バイト・1,460 バイト・300 バイトの 3 セグメントを続けて送り、すべて届いた。受信側が返す ACK 番号は？
正答: `23221`。解説: 20,001 + 1,460 + 1,460 + 300 = 23,221。累積 ACK なので 3 本まとめて 1 つの番号で答えられる。

**Lv57**(表 + 入力・number)

## 4. 71〜80 経路表の深化

段の知識: 5〜8 行の経路表(直接接続 C・スタティック S・デフォルト S*・動的 O/R/B)で最長一致と出口 IF、複数ソースの AD による優先、同一 AD ならメトリック、表に無い宛先、集約が原因の誤転送と抜け(ブラックホール)。Lv7(3〜4 行の最長一致、1 段)に優先規則と行どうしの包含関係が加わる。再帰参照と「選ばれた理由」は 120〜129、プロトコルの仕組みは 400 台。

ゲーム内の規則(迷った点 5):
- **AD 値**(Cisco 社の用語「管理距離」。一般名は「経路の優先度」で、小さいほど優先)の既定値は次を使う: 直接接続 0、スタティック 1、eBGP 20、EIGRP(内部。Cisco 社の独自方式)90、OSPF 110、IS-IS 115、RIP 120、iBGP 200。表に `種別` 列(C/S/S*/O/R/B/D/i)と `AD` 列を併記する

- `Null0` は破棄用の出口 IF

## 5. 81〜90 ACL と NAT の合成

段の知識: 2〜3 行の ACL(ワイルドカード、暗黙の deny、上から順)で複数パケットの判定、適用位置(in/out)、NAT との前後(内→外は変換前、外→内は変換後に評価)、ポートフォワードの宛先書き換え。Lv9・Lv10 の単体の読みが「順序・適用位置・NAT との前後」の合成になる。拡張 ACL の 5 項目の体系・経路上の置き場所・復路は 330〜349。

ACL の文法(迷った点 6): Lv9 と同じゲーム内の簡略文法 `行番号 permit|deny プロトコル 送信元 宛先 [eq ポート]` を使い、送信元・宛先は `アドレス ワイルドカード` / `host アドレス` / `any` で書く。問いの焦点は順序・暗黙 deny・ワイルドカード・適用位置・NAT との前後に置き、5 項目を体系的に問うのは 330〜349 に残す。

ルータのモデル(2 IF 固定): `Gi0/0` = 内側(10.x.y.0/24)、`Gi0/1` = 外側(203.0.113.N)。NAPT の内側グローバルは外側 IF のアドレス。処理順(ゲーム内の規則。一般的なルータの動作に合わせる):
- 内 → 外: `Gi0/0 in` の ACL(**変換前**: 送信元は内側ローカル)→ 経路決定 → NAT(送信元を内側グローバルに)→ `Gi0/1 out` の ACL(**変換後**)
- 外 → 内: `Gi0/1 in` の ACL(**変換前**: 宛先は内側グローバル)→ NAT(宛先を内側ローカルに。ポートフォワードならポートも)→ 経路決定 → `Gi0/0 out` の ACL(**変換後**)
- ACL はパケットの流れと同じ IF・方向のものだけが評価される(`Gi0/0 in` は内側から入るパケットだけ)

## 6. 91〜99 アドレッシングの総合: 観測からの逆算

段の知識: ホストの設定・ARP 表・経路表・ACL・NAT 表・DNS 応答の断片から、通信できない原因(マスク不一致、ゲートウェイがサブネット外、重複アドレス、経路の抜け、TTL 切れ、ACL の該当行、NAT の抜け、逆引き不一致)を 1 つ特定する。または要件から IPv4/IPv6 のアドレス計画を書く。複数の情報源を照合して矛盾から推論する。コマンドで観測を自分で集めるのは 160〜199(ここでは表を与える)。

方式: **シナリオ生成器(plant-then-perturb)**。正常に疎通する小さな構成(ホスト 2〜4 台、ルータ 1〜3 台、サーバー 1 台)を NetGen の最小版で作り、既知の誤りを**ちょうど 1 つ**注入し、シミュレータ(最小版: 同一サブネット判定・ARP・最長一致転送・TTL・ACL・NAT・DNS 照合)で「注入前は疎通し、注入後は疎通しない」ことを確認してから保存する。検証器は**別実装**で原因候補 8 種をすべて試し、観測(与える表)と矛盾しない原因が注入したものだけ(一意)であることを確認する。

答えの形(迷った点 7): 91〜97 は原因の種類が段で決まっているので「該当箇所」(機器名・IP・行番号・ネットワーク)を入力する。98 は原因の種類が 8 種から 1 つなので「原因の分類語」を `token` で入力する(語彙表は 6.3)。99 は複数プレフィックスの `prefixplan`。

ゲーム内の規則(迷った点 8): 公開サーバーは「接続元の逆引き名を正引きした結果が接続元アドレスに一致しないと接続を拒否する」設定にできる。逆引き不一致はこの設定のサーバーに対する失敗原因としてだけ出す。

### 6.2 例題

**Lv91**(表 2 つ + 入力・devname)
問: PC1 から PC2 へ ping が届かない。設定が誤っているホストは？
R1 の IF: Gi0/0 10.0.5.1/24
| ホスト | IP | マスク | GW |
|---|---|---|---|
| PC1 | 10.0.5.10 | 255.255.255.0 | 10.0.5.1 |
| PC2 | 10.0.5.200 | 255.255.255.128 | 10.0.5.1 |
| PC3 | 10.0.5.77 | 255.255.255.0 | 10.0.5.1 |
正答: `PC2`。解説: PC2 は /25 なので自分のサブネットを 10.0.5.128〜255 と考える。PC1(10.0.5.10)は外に見えて GW に送ろうとするが、GW 10.0.5.1 も範囲外なので ARP できず送れない。ルータの IF が /24 なので正しいマスクは 255.255.255.0。守る側: 配布は DHCP に統一し、手動設定の機器はマスクを点検する。

**Lv94**(表 3 つ + 入力・devname)
問: PC1(10.0.5.10)から SRV1(10.0.7.10)へ ping すると「要求がタイムアウトしました」。経路が欠けているルータは?(R1 — R2 間は 10.0.0.0/30、R2 — R3 間は 10.0.0.4/30)
| R1 | R2 | R3 |
|---|---|---|
| 10.0.5.0/24 C Gi0/0 | 10.0.0.0/30 C Gi0/0 | 10.0.0.4/30 C Gi0/0 |
| 10.0.0.0/30 C Gi0/1 | 10.0.0.4/30 C Gi0/1 | 10.0.7.0/24 C Gi0/1 |
| 10.0.7.0/24 S → 10.0.0.2 | 10.0.7.0/24 S → 10.0.0.6 | 10.0.0.0/30 S → 10.0.0.5 |
| | 10.0.5.0/24 S → 10.0.0.1 | |
正答: `R3`。解説: 往路は R1 → R2 → R3 → SRV1 と届く。応答は SRV1 → R3 に戻るが、R3 に 10.0.5.0/24 の行が無い(10.0.0.0/30 だけ)ので破棄される。「タイムアウト」は往路だけ届いた典型。

**Lv95**(図 + 入力・devname)
問: PC1 → R1 → R2 → R3 → SRV1 の経路で、PC1 の初期 TTL が 2 に設定されている。PC1 のパケットを破棄して ICMP 時間超過を返すルータは？
正答: `R2`。解説: R1 で 2 → 1 に減って転送。R2 で 1 → 0 になり、R2 が破棄して時間超過(Type 11)を返す。

**Lv98**(表 + 入力・token)
問: PC1(10.0.5.9)から公開サーバー SRV1(逆引き一致を必須にしている)への接続が拒否される。原因の分類語を入力(mask / gateway / duplicate / route / ttl / acl / nat / dns。日本語でもよい)。
与える表: PC1 の設定(正常)、R1 の経路表(正常)、ACL(permit any)、NAT 表(10.0.5.0/24 が対象)、DNS 応答: `pc1.shibuya.example. A 10.0.5.9` / `9.5.0.10.in-addr.arpa. PTR pc1-old.shibuya.example.` / `pc1-old.shibuya.example. A 10.0.5.19`
正答: `dns`(別名: 逆引き、逆引き不一致、PTR)。解説: PTR が指す名前 pc1-old を正引きすると 10.0.5.19 で、接続元 10.0.5.9 と一致しない。他の表に矛盾は無い。守る側: ホストの改名時は A と PTR を同時に更新する。

**Lv99**(入力・prefixplan)
問: 親ブロック 10.40.0.0/16 と 2001:db8:40::/48 を、次の 4 拠点に割り当てる。IPv4 は必要ホスト数の大きい順に先頭から詰め、IPv6 は同じ順に /64 を 0 から振る。各拠点を「拠点名 IPv4 IPv6」で 1 行ずつ。
要件: honten 500 台、shitenA 120 台、shitenB 60 台、shitenC 25 台
正答(正準解):
```
honten  10.40.0.0/23     2001:db8:40::/64
shitenA 10.40.2.0/25     2001:db8:40:1::/64
shitenB 10.40.2.128/26   2001:db8:40:2::/64
shitenC 10.40.2.192/27   2001:db8:40:3::/64
```
解説: 500 台 → /23(510)、120 → /25(126)、60 → /26(62)、25 → /27(30)。大きい順に置くと境界が自然に揃う。判定は制約充足なので、別の正しい配置(重ならず・親に収まり・要件を満たす)も正解。

### (c) 実装順の提案

依存関係(LEVELS.md 第 6 章)に従い、土台 → 計算生成 → FactBank → シナリオ生成の順。各段は「生成器 + 検証テスト + `index.js` への登録」を 1 単位とし、`npm.cmd test` に追加してから次へ進む。

1. **土台**(#1 #2 #3): `rng.js`、`normalize.js` + `test/normalize.js`、問題形式に `answerKind/format/inputHint/accept` を足す、`world.answer` の入力判定、画面の入力欄(1.2)。既存 Lv1〜10 は変更しない(4 択のまま動く)
2. **51〜60 の計算生成**(55〜60)→ `transport.js`。既存の `buildOptions` と `toIp` を再利用。NAPT 行追加の規則(迷った点 1)はここで固定
3. **71〜80 の計算生成**(71・72・75〜80)→ `routing.js`。Lv7 `routeTable` の拡張。表に種別・AD・IF 列を足す
4. **81〜90 の計算生成**(81〜84・86〜90)→ `aclnat.js`。Lv9 `aclEval` を参照しつつ、検証は別実装
5. **61〜70 の計算生成**(63・64・65 の読み・67〜70)→ `dhcpdns.js`
6. **FactBank**(`facts.json`)の下書きと人確認 → 51〜54・61・62・65 の役割・66・73・74・85 の固定テンプレート。ここまでで 51〜90 の全レベルに少なくとも 1 生成器が揃う
7. **95・99・100**(計算で決まるが題材は総合)→ `diagnose.js` の `diagTtl`・`addrPlan`・`planVerifier`、`l2switch.js`
8. **最小 NetGen + 最小シミュレータ**(#9 #10 の最小版)→ `server/sim/`。既知の構成でテスト
9. **91〜94・96〜98 のシナリオ生成器**(#12)→ 独立検証器(8 種総当たり)を先に書き、生成器を後に書く(plant-then-perturb)

### (d) 判断に迷った点(ユーザーに決めてもらうこと)

1. **NAPT のポート付け替え規則**(Lv59・60・89): 本書は「衝突した番号から 1 ずつ上げて最初の空き」に固定した。実機では実装依存(乱数、最小空き、範囲内の順送り)。ゲーム内規則としてこれでよいか。別案は「1024 以上の最小の空き」
2. **DHCP Offer/Ack の宛先**(Lv62): ブロードキャストフラグを立てた前提で `255.255.255.255` に固定した。実機ではユニキャストの実装もある。問題文に「ブロードキャストフラグを立てている」と毎回書く方針でよいか
3. **リレーの送信元アドレス**(Lv63): `giaddr` と同じ(クライアント側 IF)に固定した。実機ではサーバー側 IF から送る実装もある。問うのは `giaddr` と宛先に限り、送信元は解説だけに書く案もある
4. **1 問 1 答の徹底**: 「next-hop と出口 IF」のような 2 要素の答えは、レベルごとに 1 要素(71 は IF、72 は next-hop)に分けた。2 要素を `next-hop IF` のように 1 行で入力させる案(正規化は順不同)もある。どちらにするか
5. **AD 値の扱い**(Lv74〜80): Cisco 社の既定値を「ゲーム内の既定値」として採用し、標準名「経路の優先度」を併記する。EIGRP(Cisco 独自)の 90 を FactBank に含めるか(`terms.json` にはある)。含めない場合は 7 行
6. **81〜90 の ACL 文法**: LEVELS.md は「標準 ACL(送信元のみ)」としているが、標準 ACL だけでは「外→内は変換後に評価」(宛先の書き換え)が問えない。本書は Lv9 と同じ簡略文法(宛先・ポートを含む)を使い、拡張 ACL の 5 項目の体系・置き場所・復路を 330〜349 に残した。この線引きでよいか
7. **91〜98 の答えの形**: 91〜97 は該当箇所(機器名・IP・行番号・ネットワーク)の入力、98 だけ分類語(`token`)の入力にした。LEVELS.md の「入力(原因の該当箇所)」に沿う形だが、分類語を 4 択にする(入力の語彙の揺れを避ける)案もある
8. **逆引き不一致を「通信できない原因」にする規則**(Lv98): 公開サーバーが PTR と A の一致を要求する設定、というゲーム内規則を置いた。採用するか、逆引きは 220〜239(DNS)に送って 98 を 7 種にするか
9. **ドメインの接尾辞**: `.example`(RFC 2606 予約。実在しない)を使う案。LEVELS.md の「ゲーム内専用の接尾辞」を別に決める(例: `.pcq`)なら、安全リンタの許可リストと合わせて 1 つに決めたい
10. **seq 番号の 2^32 折り返しと FIN**(Lv55・56): 折り返しは出さず、FIN(1 バイト消費)は解説だけに書いた。Lv56 の最難化として入れるか
11. **Lv99 の採点**: 正準解(大きい順・同数は拠点名順)を `accept` に置きつつ、判定器は制約充足で別解も正解にする。「正準解のみ正解」にすれば実装は軽いが、正しい計画を不正解にする。どちらか
12. **エフェメラルポートの範囲**(Lv54): IANA の 49152〜65535 に固定し、OS 差のある 32768〜49151 を選択肢に出さない。問題文に「IANA の推奨範囲」と書くか
13. **その場生成か保存か**: 51〜100 の計算生成は正確さの点ではその場生成でも問題ないが、8.13(拠点に紐づき、クリアまで同じ問題)に従うなら seed を保存する必要がある。「seed だけ保存し本文は再生成」(軽い)か「DB.md 3.4 どおり rendered も保存」(版が変わっても再現できる)か。未決 #8(本数・更新間隔・拠点専用か共有か)と一緒に決めたい
14. **既存 Lv1〜10 の乱数**: `Math.random` のまま(その場生成)でよいか、`makeRng(seed)` に揃えるか。揃えるなら `subnet.js` / `basics.js` の `rand/pick/shuffle` を引数で受け取る形にする小さな改修が要る
15. **Lv73 の形式**: デフォルトが無いときの動作を 4 択、あるときを入力にした(1 レベルに 2 形式)。段の中で形式を 1 つに揃える(両方 4 択)方がよいか
16. **入力の再入力**: 形式が違う入力(IP の桁数が足りない等)も「不正解」として扱う案にした(再入力を許すと総当たりできるため)。形式エラーだけは 1 回再入力を許すか(SECURITY.md の「画面は信用しない」原則と、待ち時間倍増 F4 との整合を見て決める)
