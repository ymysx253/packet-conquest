## 0. 読み方と共通の約束

### 0.1 既存(Lv1〜10)との境界

| 既存のレベル | 既存の題材(すべて 4 択) | 11〜50 で重ねないこと |
|---|---|---|
| Lv1〜3 `subnet.js` | マスク・ネットワーク・ブロードキャスト・ホスト数・同一ネットワーク判定(/8・/16・/24 → /25〜/28 → /19〜/23・/29・/30)。1 つの値を**選ぶ** | 11〜20 は**入力式**で、複数の値・N 番目・所属番号・基数変換という 2〜3 段の計算を自分で組む |
| Lv4 | 必要ホスト数 → 最小プレフィックス(1 区画)、ワイルドカード | 21〜30 は 3〜6 区画を**同時に**配置する。1 区画の最小プレフィックスだけを問わない |
| Lv5 | 境界に揃った 2〜4 ブロックの集約、IPv6 の省略表記 | 19・28 は「非 16 ビット境界の IPv6 プレフィックス」「分けた区画の再集約と巻き込み」に限る |
| Lv6 | IPv6 の種別(GUA/ULA/LLA/マルチキャスト)4 択、/32・/48・/64 のプレフィックス | 31〜40 は IPv4 の種別、IPv6 の特殊アドレス(未指定・ループバック・ff02::1/::2・ソリシテッドノード)、EUI-64、**挙動**の規則 |

| Lv8 | ARP 表 / MAC 表を 1 つ読む | 48 は ARP 表と MAC 表の**2 表合成**、42〜50 は区間ごとのヘッダの変化 |
| Lv9・10 | ACL・NAT 表 | 11〜50 では扱わない(81〜90) |

### 0.2 問題オブジェクトの拡張(第 6 章 #1「問題の共通形式」への提案)

既存の `{ text, options, answerIndex, explanation, table, meta }` に、入力式のために次を足す。**答えはサーバーだけが持つ**(クライアントには `text / table / answerKind / fields の label・kind` だけ送る)。

```
{
  text, table?, explanation, defenseNote, meta,
  answerKind: 'choice' | 'text',
  // choice のとき(既存どおり)
  options, answerIndex,
  // text のとき
  fields: [ { name, label, kind, accept: [正規化済み正解…] } , … ],
  compare: 'ordered' | 'set'       // set は VLSM(同サイズ区画の入替を許す)だけ
}
```

- `kind` は `ipv4 / ipv6 / cidr4 / cidr6 / prefixlen / int / bin / hex / mac / yesno / term`。判定器(#2)は kind ごとの正規化関数を持ち、`accept` のどれかに一致すれば正解
- 複数欄は**全欄一致で正解**(部分点は作らない。突破は正解 1 回の原則)
- `meta` にはテスト用の真の値(パラメータと中間値)を入れ、配信しない(既存どおり)

### 0.3 入力の正規化規則(判定器 #2。この表自体をテストする)

| kind | 正規化 | 受け付ける例(→ 正規形) |
|---|---|---|
| `ipv4` | 全角→半角、前後の空白除去、各オクテットの先頭 0 を除く、4 オクテットで 0〜255 でなければ不正解 | `０１０.0.0.1` → `10.0.0.1`、`010.077.200.0` → `10.77.200.0` |
| `ipv6` | 全角→半角、小文字化、`::` を展開して 8 ヘクステットの数値列にして比較(RFC 5952 の正規形に戻す)。末尾の `/n` は無視しない(別 kind) | `2001:0DB8:0:0:0:0:0:1` = `2001:db8::1` |
| `cidr4` / `cidr6` | アドレス部は上記、`/` は全角 `／` も可、プレフィックス長は整数。**アドレス部がネットワークアドレスでないときは不正解**(`10.0.0.5/24` は `10.0.0.0/24` と同一視しない) | `１０.0.0.0／２４` → `10.0.0.0/24` |
| `prefixlen` | `/21`、`21`、`／21` を同一視。ドット表記のマスク(`255.255.248.0`)も連続ビットなら同一視 | `/21` = `21` = `255.255.248.0` |
| `int` | 全角→半角、カンマ区切り(`1,024`)と全角カンマを除く、`番目` `個` `台` `アドレス` などの単位語を末尾から除く | `１,５５６番目` → `1556` |
| `bin` | 空白・`.`・`_` を除く、先頭 0 の有無を同一視(ただし問題文が「8 桁で」と指定したら桁数も見る) | `1011 0010` = `10110010` |
| `hex` | 小文字化、`0x` を除く、先頭 0 の有無を同一視 | `0xE5` = `e5` |
| `mac` | 小文字化、`:` `-` `.` を除いて 12 桁の 16 進にする。OUI/機器部(6 桁)も同じ | `00-00-5E-00-53-7A` = `0000.5e00.537a` = `00:00:5e:00:53:7a` |
| `yesno` | `○ ◯ はい yes する 転送する 使える` → `yes`、`× ✕ いいえ no しない 転送しない 使えない` → `no` | |
| `term` | FactBank の語彙 id に対応する別名表で正規化(全角半角・空白・「アドレス」の有無を無視)。表にない語は不正解 | `リンクローカル`, `APIPA`, `link-local` → `v4-linklocal` |

### 0.4 4 択の誤答(ダミー)の共通規則

- 正解と**値として**重複しないこと(文字列ではなく正規化後の値で比較)。`buildOptions` の流儀を踏襲し、候補が足りないときの filler も正解と異なることを確認する
- 「ありがちな間違い」から作る: 境界の取り違え(ブロードキャスト↔ネットワーク、最初↔最後)、プレフィックス ±1、0 始まり↔1 始まり、ビット反転忘れ、反転するビットの位置違い(0x02 ↔ 0x01 / 0x80)、ff:fe の挿入位置違い、10 進↔16 進の読み違い、オクテット境界で丸める誤り
- 入力式が主のレベルでも、誤答の作り方を書いてあるのは **(a) #2 判定器ができるまでの暫定 4 択配信**(第 9 章 迷った点 1)と **(b) 解説で「よくある間違い」を示す**ため

### 0.5 乱数と保存

- 生成器は `rng` を引数で受け取る(例: mulberry32 を seed から作る)。`Math.random` を直接使わない。これで (テンプレート id, seed, 版) から同じ問題が再現できる(LEVELS.md 第 5 章 seed 方式、DB.md 3.4)
- 11〜30 は純粋な計算生成なので**その場生成もできる**。固定問題(拠点 × レベルで active 1 つ、クリアで差し替え)として保存するかは 8.13 の方針に従う(第 9 章 迷った点 12)
- 保存時は `rendered`(text・table・fields の label/kind・options)と `answer`(index または accept)の両方を保存する

### 0.6 安全(3.5・LEVELS.md 第 5 章)

- IPv4 内側: `10/8`・`172.16/12`・`192.168/16`。外側・文書用: `192.0.2.0/24`・`198.51.100.0/24`・`203.0.113.0/24`。IPv6: `2001:db8::/32`・`fd00::/8`・`fe80::/10`・`ff02::/16`
- MAC アドレス: 機器のものは**ローカル管理ビット立て**(第 2 桁が 2・6・a・e)。EUI-64 の反転を「0 → 1」でも見せたいときは RFC 7042 の**文書用ユニキャスト MAC `00:00:5e:00:53:00`〜`00:00:5e:00:53:ff`** を使う(実在ベンダーの OUI を避けつつグローバル管理の例が作れる)
- 機器名は `devices.json` の付け方(R1、SW1、PC1、L3SW1、IF は Gi0/0・Gi1/0/1)。メーカーは架空の「PC ネットワークス」。ホスト名の接尾辞はゲーム内専用
- 本文・解説・defenseNote・誤答は安全リンタ(#7)を通す。攻撃手法の名前・手順は書かない

### 0.7 守る側の注記(defenseNote、#8 攻守同重)

計算・規則の問題では「守る側ならどう使うか」が薄くなるため、段ごとに定型を用意し、生成器がパラメータを差し込む。
- 11〜20: 「サブネットの境界を正しく切れると、ACL や経路の対象範囲を取りこぼさない」
- 21〜30: 「必要数ぴったりでなく成長分を見込み、集約できる並びにしておくと経路表と ACL が短くなる」
- 31〜40: 「境界で落とすべき種別(プライベート・リンクローカル・文書用)を知っていると、外から来てはいけない送信元を見分けられる」
- 41〜50: 「区間ごとに変わる項目(MAC・TTL)と変わらない項目(IP)を知っていると、キャプチャの異常(MAC と IP の不一致)に気づける」

## 1. レベル 11〜20: アドレス計算を自分で組み立てる

段の定義(LEVELS.md): 任意プレフィックス(/9〜/30)でネットワーク・ブロードキャスト・使用可能範囲の両端・N 番目のサブネット・あるホストが属するサブネットの番号を求める。2 進・16 進の相互変換を計算の一部として含む。解答は入力。生成は計算生成、検証はビット演算の別実装。

### 1.1 一覧

|---|---|---|---|---|---|---|---|

### 1.2 各レベルの詳細

#### Lv11 2 進 ⇄ 10 進(1 オクテット)

- 生成: `rng` で 0〜255 を 1 つ。方向(2 進→10 進 / 10 進→2 進)を半々。境界値(0, 1, 127, 128, 254, 255)を 1/8 の確率で選ぶ
- 誤答: ビット順を逆に読んだ値、最上位ビットを落とした値、±1、位の重みを 1 つ取り違えた値(例: 32 を 16 に)
- 検証: 1 万件。`parseInt(bin, 2)` と `n.toString(2).padStart(8,'0')` で解き直し。全数(256 × 2 方向)も可。`bin` 正規化が `1011 0010` を受けることを判定器テストで確認
- 例題 1: 「2 進数 `10110010` を 10 進数で答えてください。」→ **178**。解説: 128+32+16+2 = 178
- 例題 2: 「10 進数 203 を 8 桁の 2 進数で答えてください。」→ **11001011**。解説: 128+64 = 192、+8 = 200、+2+1 = 203 → 1100 1011

#### Lv12 16 進 ⇄ 2 進 ⇄ 10 進

- 生成: ヘクステット(0〜0xffff)か MAC のバイト(0〜0xff)。向きは 16→2、2→16、16→10 の 3 通り。ヘクステットは `2001:db8:xxxx:…` の一部として文脈を付けてもよい
- 誤答: ニブルの順を逆にした値、1 ニブルだけ ±1、`b` と `d` の取り違え(1011 ↔ 1101)、10 進で 16 進をそのまま読んだ値(`0x1a` → 110)
- 検証: 1 万件、別実装(`parseInt(x,16)` ↔ `toString(2)`)。`hex` 正規化が大文字・`0x` 付きを受けること
- 例題 1: 「IPv6 アドレス `2001:0db8:…` の 2 番目のヘクステット `0db8` を 16 桁の 2 進数で。」→ **0000110110111000**。解説: 0→0000、d→1101、b→1011、8→1000
- 例題 2: 「2 進数 `11100101` を 16 進 2 桁で。」→ **e5**。解説: 1110 → e、0101 → 5

#### Lv13 MAC アドレスの構造

- 生成: 文書用 `00:00:5e:00:53:xx` とローカル管理 MAC(第 1 バイトの下位 2 ビットを 0b10 に)を半々。問いは「OUI」「機器識別部」「ローカル管理か(U/L)」「マルチキャスト宛か(I/G)」から 2 つ(欄 2 つ)
- 誤答: 境目を 16 ビット・32 ビットで切った値、I/G と U/L を入れ替えた判定、最上位ビットで判定した値
- 検証: 1 万件。OUI = 先頭 6 桁、U/L = 先頭バイト & 0x02、I/G = 先頭バイト & 0x01 を文字列処理の別実装で確認。生成した MAC が安全範囲(第 2 桁 2/6/a/e または 00:00:5e:00:53)にあることも assert
- 例題 1: 「MAC アドレス `00:00:5e:00:53:7a` の OUI(メーカー識別部)と機器識別部を答えてください。」→ **00:00:5e** / **00:53:7a**
- 例題 2: 「MAC アドレス `02:1a:4f:33:c0:9d` は (a) ローカル管理アドレスか、(b) マルチキャスト宛のアドレスか、○×で。」→ (a) **○** (b) **×**。解説: 先頭バイト 02 = 0000 0010。最下位ビット(I/G)が 0 なのでユニキャスト、下から 2 番目(U/L)が 1 なのでローカル管理

#### Lv14 任意プレフィックスのネットワークとブロードキャスト

- 生成: 拠点の `base` から /9〜/30(/16・/24 を除く)でアドレスを 1 つ。境目が第 2・第 3・第 4 オクテットのどこに来るかを均等に。2 欄(ネットワーク、ブロードキャスト)
- 誤答: 境目を 1 オクテット隣で丸めた値、ブロック幅を 2 倍/半分にした値、ネットワークとブロードキャストの入替、ブロードキャスト −1
- 検証: 1 万件。生成器は 32 ビット整数演算、検証器は**2 進文字列の先頭 p 桁を残して 0/1 で埋める**別実装。両端を独立に assert。/9 と /30 を必ず含む
- 例題 1: 「`172.16.200.77/13` のネットワークアドレスとブロードキャストアドレスを答えてください。」→ **172.16.0.0** / **172.23.255.255**。解説: /13 は第 2 オクテットに境目があり、ブロック幅 8。16 は 8 の倍数なのでそのまま 16。範囲は 172.16〜172.23
- 例題 2: 「`10.77.203.150/21`」→ **10.77.200.0** / **10.77.207.255**。解説: 第 3 オクテットでブロック幅 8。203 を 8 の倍数に切り捨てて 200、末尾は 207

#### Lv15 使用可能範囲の両端

- 生成: /9〜/30。2 欄(最初のホスト、最後のホスト)。/30 を 1/6 で混ぜる(使えるのが 2 つだけ)
- 誤答: ネットワーク/ブロードキャストそのもの、+2/−2、隣のブロックの両端
- 検証: 1 万件、別実装(Lv14 の文字列方式 +1/−1)。最初 < 最後、両方が同じネットワークに属することを assert
- 例題 1: 「`192.168.37.130/26` のサブネットで、機器に割り当てられる最初と最後のアドレスは?」→ **192.168.37.129** / **192.168.37.190**。解説: ブロック幅 64。130 は 128〜191 の範囲。ネットワーク .128 の次が最初、ブロードキャスト .191 の手前が最後
- 例題 2: 「`10.200.14.9/11`」→ **10.192.0.1** / **10.223.255.254**。解説: 第 2 オクテットでブロック幅 32。200 → 192〜223

#### Lv16 あるホストが属するサブネットの番号

- 本文で**「最初のサブネットを 1 番目とする」**と明記する(0 始まりは採らない。第 9 章 3)
- 生成: 親 /p1(8〜22)と分割後 /p2(p1+2〜p1+8、ただし p2 ≤ 30)、親の中のアドレスを 1 つ。2 欄(何番目か、その区画の CIDR)
- 誤答: 0 始まりの番号(正解 −1)、+1、親ではなくクラス境界から数えた番号、区画サイズを 2 倍にした番号
- 検証: 1 万件。別実装: `Math.floor((ip − parent) / 2^(32−p2)) + 1`。区画 CIDR の先頭 ≤ ip ≤ 区画の末尾を assert。分割数 2^(p2−p1) ≥ 番号 を assert
- 例題 1: 「`192.168.0.0/16` を /20 のサブネットに等分した。最初を 1 番目とすると、`192.168.77.5` は何番目のサブネットに属するか。その CIDR も答えよ。」→ **5** / **192.168.64.0/20**。解説: /20 の幅は第 3 オクテットで 16。77 → 64。64 ÷ 16 = 4 なので 0 始まりで 4、1 始まりで 5 番目
- 例題 2: 「`10.8.0.0/14` を /18 に等分(16 個)。`10.10.200.33` は何番目か。」→ **12** / **10.10.192.0/18**。解説: 親の先頭からのオフセットは (10−8)×65536 + 200×256 + 33 = 182,305。/18 の幅 16,384 で割ると 11.1 → 0 始まりで 11、1 始まりで 12 番目。先頭は 10.8.0.0 + 11×16,384 = 10.10.192.0

#### Lv17 N 番目のサブネットのアドレス

- 生成: 親 /p1、分割 /p2、N(1〜2^(p2−p1))。2 欄(分割数、N 番目の CIDR)
- 誤答: N−1 番目・N+1 番目、親の先頭(1 番目)、分割数を 2^(p2−p1−1) にした値
- 検証: 1 万件。別実装: 親 + (N−1) × 2^(32−p2)。結果が親に含まれ、/p2 境界に揃っていることを assert
- 例題 1: 「`172.20.0.0/16` を /19 に等分した。6 番目のサブネットは?(分割数も答えよ)」→ **8** / **172.20.160.0/19**。解説: 幅は第 3 オクテットで 32。0, 32, 64, 96, 128, 160 … の 6 番目は 160
- 例題 2: 「`10.64.0.0/12` を /15 に等分。3 番目は?」→ **8** / **10.68.0.0/15**。解説: /15 は第 2 オクテットで幅 2。64, 66, 68 → 3 番目は 68

#### Lv18 N 番目のサブネットの範囲

- 生成: 17 と同じパラメータで、4 欄(ネットワーク・ブロードキャスト・最初のホスト・最後のホスト)
- 誤答: 17 の誤答 + 15 の誤答
- 検証: 1 万件。17 の別実装 + 両端の別実装。4 値の大小関係(net < first < last < bcast)を assert
- 例題 1: 「`192.168.100.0/24` を /27 に等分した 4 番目のサブネットの、ネットワーク・ブロードキャスト・最初・最後のホスト。」→ **192.168.100.96** / **.127** / **.97** / **.126**。解説: 幅 32。0, 32, 64, 96 の 4 番目が 96
- 例題 2: 「`10.50.0.0/16` を /22 に等分した 23 番目。」→ **10.50.88.0** / **10.50.91.255** / **10.50.88.1** / **10.50.91.254**。解説: /22 は第 3 オクテットで幅 4。(23−1)×4 = 88

#### Lv19 IPv6 の非 16 ビット境界プレフィックスと N 番目の /64

- 生成: (a) `2001:db8:` 以下を乱数で埋めたアドレスと /36・/40・/44・/52・/56・/60 → プレフィックス(`cidr6`)。(b) `/48` または `/56` の親を /64 に分けた N 番目(N ≤ 256)。Lv6 の /32・/48・/64 は出さない
- 誤答: 16 ビット境界で切った値(/48 や /64 で切る)、ニブルを 1 つ余計に残す/落とす、N を 10 進のまま 16 進の位置に書く(18 番目 → `:18:` と書く誤り。正解は `:11:` と `:12:` の違いに注意)、N−1 のずれ
- 検証: 1 万件。別実装: 128 ビットを BigInt にしてマスク。`ipv6` 正規化(RFC 5952)は `test/basics.js` の `expandV6` 方式で展開して比較。N 番目は親 + (N−1) << 64 で再計算
- 例題 1: 「`2001:db8:5c7e:9a31:abcd::1` が属する /52 のプレフィックスは?」→ **2001:db8:5c7e:9000::/52**。解説: /52 = 48 + 4 ビット。4 番目のヘクステット `9a31` の先頭 1 ニブル `9` だけを残す
- 例題 2: 「`2001:db8:4a00::/56` を /64 に等分(256 個)。最初を 1 番目として 18 番目は?」→ **2001:db8:4a00:11::/64**。解説: /56 → /64 の 8 ビットは 4 番目のヘクステットの下位バイト。18 番目は 0 始まりで 17 = 16 進 `11`

#### Lv20 2 進表記からの総合

- 生成: /17〜/29 のアドレスとマスクを**2 進のドット区切り**で見せる。3 欄(プレフィックス長、ネットワーク CIDR、サブネット内で何番目のホストか = アドレス − ネットワーク。最初のホストを 1 番目と明記)
- 誤答: 1 の数の数え違い(±1)、ホスト番号を 0 始まりにした値、ネットワークではなくブロードキャストから数えた値
- 検証: 1 万件。2 進文字列 → 10 進 → Lv14/16 の別実装。ホスト番号 ∈ [1, 2^(32−p) − 2] を assert
- 例題 1: 「アドレス `11000000.10101000.00001010.01001011`、マスク `11111111.11111111.11111111.11100000`。プレフィックス長、ネットワーク(CIDR)、このアドレスはそのサブネットの何番目のホストか(最初のホストを 1 番目)。」→ **/27** / **192.168.10.64/27** / **11**。解説: 1 が 27 個。最終オクテット 01001011 = 75、幅 32 で 64 に切り捨て。75 − 64 = 11
- 例題 2: 「`00001010.00011001.10110110.00010100`、マスク `11111111.11111111.11110000.00000000`」→ **/20** / **10.25.176.0/20** / **1556**。解説: 第 3 オクテット 182 を幅 16 で 176 に。(182−176)×256 + 20 = 1,556

## 2. レベル 21〜30: アドレス空間の設計(VLSM)

段の定義: 親ブロック(/16〜/22)を 3〜6 区画の必要ホスト数に割り当てる。大きい順の配置、各区画のプレフィックスと範囲、未使用領域、足りるか・足りないか、再集約できる条件。解答は入力(複数のプレフィックス)。生成は計算生成(要件を乱数で作り親に収まるものだけ出題)。検証は独立の検証器で「重ならない・親に収まる・各要件を満たす・総使用量が最小」。同点は集合比較。

### 2.1 配置の規則(本文に毎回明記する固定文)

> 必要台数 + 2(ネットワークとブロードキャスト)が収まる最小のブロックを各区画に与え、**ブロックの大きい順に親の先頭から隙間なく**並べる。同じ大きさの区画の順番は問わない。

この規則の下では、ブロックがすべて 2 の冪で降順なので整列の無駄が出ず、**総和 ≤ 親サイズ なら必ず収まり、配置は(同サイズの入替を除いて)一意**になる。Lv27 だけ「書かれた順に置く」別規則を使う(その場合も「次の整列位置」で一意)。

### 2.3 共通の生成・検証

- **生成**: 親 /p と区画数 n を決め、ホスト数は「2 の冪 −2 の近く(126, 254, 510 など)」「中途半端(60, 300)」「小さい(5, 10)」を混ぜる。各区画の最小ブロックを計算し、**総和 ≤ 親サイズ**になるまで引き直す(26 だけ収まらないケースも出す)。区画名は架空の部署名表(営業・開発・総務・来客・サーバー・無線・倉庫・受付 …)から重複なしで選ぶ
- **検証器(別実装)**: 答えの区画集合に対して (1) どの 2 区画も重ならない、(2) すべて親に含まれる、(3) 各区画のサイズ −2 ≥ 必要台数、(4) 各区画が自分のサイズに整列している、(5) 総使用量 = Σ最小ブロック(最小性)、(6) 大きい順に隙間なく(21〜26・28・30)または書かれた順の次の整列位置(27・29)を、生成器とは別の素朴なループ(先頭から 1 アドレスずつ走査して置く)で再現し一致。1 万件
- **集合比較**: 同サイズ区画の入替を許す。判定器は `fields` を (サイズ, CIDR) の多重集合として比べ、区画名は表示用。欄の数と各欄のサイズが要件から決まるので、入れ替えても一意に照合できる
- **誤答(暫定 4 択用)**: 1 区画だけプレフィックス ±1、2 区画の順を小さい順にした配置、整列を無視して詰めた配置(重なり)、親の外にはみ出た配置

### 2.4 各レベルの詳細

#### Lv21 3 区画のプレフィックス長
- 例題 1: 「親 `192.168.8.0/22` を、営業 120 台・開発 60 台・サーバー 25 台の 3 区画に分ける。大きい順に各区画のプレフィックス長を答えよ。」→ **/25, /26, /27**。解説: 122 → 128 = 2^7 → /25、62 → 64 → /26、27 → 32 → /27
- 例題 2: 「親 `10.3.0.0/16`、区画: 500 台、200 台、1000 台。」→ **/22, /23, /24**。解説: 大きい順に並べ替えてから: 1002 → 1024 → /22、502 → 512 → /23、202 → 256 → /24

#### Lv22 3 区画の CIDR
- 例題 1: 「親 `172.16.40.0/22`、A 200 台、B 50 台、C 20 台。各区画の CIDR。」→ **A 172.16.40.0/24、B 172.16.41.0/26、C 172.16.41.64/27**。解説: 256 + 64 + 32。A の次(.41.0)に B、B の次(.41.64)に C
- 例題 2: 「親 `10.9.0.0/20`、1500 台・300 台・100 台。」→ **10.9.0.0/21、10.9.8.0/23、10.9.10.0/25**。解説: 2048 + 512 + 128 = 2688 ≤ 4096

#### Lv23 4 区画の CIDR(同サイズを含む)
- 例題 1: 「親 `192.168.64.0/23`、本社 100・支店 100・工場 40・管理 10。」→ **192.168.64.0/25、192.168.64.128/25、192.168.65.0/26、192.168.65.64/28**(本社と支店は入替可)。解説: 128 + 128 + 64 + 16 = 336。工場は 40 + 2 = 42 > 32 なので /27 では足りず /26(ここを /27 にするのがよくある間違い。誤答に使う)
- 例題 2: 「親 `10.120.0.0/19`、2000・900・400・60。」→ **10.120.0.0/21、10.120.8.0/22、10.120.12.0/23、10.120.14.0/26**。解説: 2048 + 1024 + 512 + 64 = 3648 ≤ 8192

#### Lv24 指定区画の使用可能範囲と未使用数
- 例題 1: 「親 `172.16.0.0/22`、300・120・50・20・6 台。大きい順に配置したとき、3 番目(50 台)の区画で使えるアドレスの最初と最後、親に残る未使用アドレス数。」→ **172.16.2.129** / **172.16.2.190** / **280**。解説: 512 + 128 + 64 + 32 + 8 = 744。3 番目は 172.16.2.128/26。1024 − 744 = 280
- 例題 2: 「親 `10.44.16.0/21`、600・250・100・30 台。2 番目の区画の両端と未使用数。」→ **10.44.20.1** / **10.44.20.254** / **608**。解説: 1024 + 256 + 128 + 32 = 1440。2 番目は 10.44.20.0/24。2048 − 1440 = 608

#### Lv25 未使用領域の CIDR 分解
- 残り範囲 [start, end] の最小 CIDR 分解は「start の整列で決まる最大ブロックを順に切る」ので一意。本文で個数 k を示す(欄の数)
- 検証: 分解の和 = 未使用数、各ブロックが整列、隣接して隙間なし、個数が最小(別実装: 貪欲法)
- 例題 1: 「Lv24 例 1 の配置で、親 `172.16.0.0/22` の未使用領域を CIDR で(3 ブロック)。」→ **172.16.2.232/29、172.16.2.240/28、172.16.3.0/24**。解説: 8 + 16 + 256 = 280
- 例題 2: 「親 `192.168.200.0/24`、60・25・10 台。未使用領域(2 ブロック)。」→ **192.168.200.112/28、192.168.200.128/25**。解説: 使うのは .0/26、.64/27、.96/28 で .111 まで。.112〜.127 が /28、.128〜.255 が /25

#### Lv26 足りるか・最小の親
- 3 欄: 収まるか(○×)、不足アドレス数(収まるなら 0)、収めるのに必要な最小の親プレフィックス長(総和を 2 の冪に切り上げ)
- 検証: 総和 ≤ 親 ⇔ 収まる(2 の冪の降順詰めで無駄が出ないことを素朴な配置で確認)
- 例題 1: 「親 `/22` に 500・500・200・100・30 台の 5 区画は収まるか。収まらなければ不足数と、収めるのに必要な最小の親を答えよ。」→ **×** / **416** / **/21**。解説: 512 + 512 + 256 + 128 + 32 = 1440 > 1024。不足 416。2048 なら収まるので /21
- 例題 2: 「親 `/21` に 1000・400・400・120・60・10 台。」→ **×** / **208** / **/20**。解説: 1024 + 512 + 512 + 128 + 64 + 16 = 2256 > 2048。不足 208。4096 = /20

#### Lv27 指定順の配置と整列の無駄
- 規則(本文に明記): 「書かれた順に、前の区画の次のアドレス以降で**自分のサイズに整列した最初の位置**に置く」。欄は各区画の CIDR(順序あり)+ 整列のため飛ばしたアドレス数
- 生成: 書かれた順が大きい順と一致しないように作る(無駄が 0 にならない)。親に収まらない順列は引き直す
- 検証: 素朴な走査で再現。飛ばした数 = 各区画の先頭 − 直前の末尾 − 1 の総和
- 例題 1: 「親 `10.70.0.0/22` に、総務 20 台 → 開発 200 台 → 来客 50 台 の順で置く。」→ **10.70.0.0/27、10.70.1.0/24、10.70.2.0/26** / 飛ばした数 **224**。解説: /27 の次は .0.32 だが /24 は 256 整列なので .1.0 へ(32〜255 の 224 個が飛ぶ)。/26 は .2.0
- 例題 2: 「親 `192.168.16.0/23`、受付 10 → 倉庫 30 → 営業 100 → 開発 250 の順。」→ **192.168.16.0/28、192.168.16.32/27、192.168.16.128/25、192.168.17.0/24** / **80**。解説: 16〜31(16 個)と 64〜127(64 個)が飛ぶ

#### Lv28 区画の再集約と巻き込み
- 2 欄: 指定 2 区画を含む最小の集約 CIDR、その集約に含まれてしまう**他の**区画の数
- 生成: Lv23 の配置を作り、2 区画を選ぶ(隣接で 0 巻き込み / 離れていて巻き込みあり を半々)
- 検証: 共通プレフィックス長を 2 進文字列で求める別実装。巻き込み数は全区画を総当たりで包含判定
- 例題 1: 「Lv23 例 1 の配置で、本社 `192.168.64.0/25` と支店 `192.168.64.128/25` を 1 行の経路にまとめる最小の集約と、巻き込む他の区画数。」→ **192.168.64.0/24** / **0**
- 例題 2: 「Lv23 例 2 の配置で、`10.120.8.0/22` と `10.120.12.0/23` をまとめると?」→ **10.120.8.0/21** / **1**。解説: 第 3 オクテット 8 = 00001000、12 = 00001100 は 5 ビット目まで同じ → /21(8〜15)。管理 `10.120.14.0/26` を含む

#### Lv29 既存割り当てへの追加
- 規則(明記): 「新しい要求を書かれた順に、空きの中で収まる最も先頭の整列位置に置く」
- 生成: 親に既存 2〜3 区画を**非連続**に置き(隙間を作る)、新規 1〜2 件。少なくとも 1 件は「最初の隙間には整列・サイズの都合で入らず、次の隙間に入る」ように作る(素朴に読むと間違う)
- 検証: 空き区間を列挙し、素朴な走査で再現。新規が既存と重ならないこと
- 例題 1: 「親 `172.16.8.0/22`。既存: `172.16.8.0/24`、`172.16.9.128/25`、`172.16.10.0/26`。新規 100 台はどこに置くか。」→ **172.16.9.0/25**。解説: /25 は 128 整列。空き .9.0〜.9.127 にちょうど収まる
- 例題 2: 「親 `10.200.0.0/16`。既存: `10.200.0.0/17`、`10.200.128.0/19`、`10.200.176.0/20`。新規 A 5000 台、B 1000 台をこの順で。」→ **A 10.200.192.0/19、B 10.200.160.0/22**。解説: A は /19(第 3 オクテット 32 整列)。160 は整列しているが 176/20 と重なるので 192。B は /22、最初の空き 160 に入る

#### Lv30 総合(6 区画 + 点対点リンク)
- LAN 区画 4〜6 と /30 のリンク 1〜3 本。全配置(`set`)と未使用 CIDR 一覧(`set`、個数明示)。リンクは「2 台 → /30」と本文で明記(/31 は使わない。第 9 章 4)
- 例題 1: 「親 `10.30.0.0/21`。本社 LAN 500、支店 LAN 200、無線 100、サーバー 60、来客 30、管理 20、ルータ間リンク 2 本(各 2 台)。全区画の CIDR と未使用領域(7 ブロック)。」→ 配置 **10.30.0.0/23、10.30.2.0/24、10.30.3.0/25、10.30.3.128/26、10.30.3.192/27、10.30.3.224/27、10.30.4.0/30、10.30.4.4/30**(来客と管理はどちらも /27 なので入替可、リンク 2 本も入替可)/ 未使用 **10.30.4.8/29、10.30.4.16/28、10.30.4.32/27、10.30.4.64/26、10.30.4.128/25、10.30.5.0/24、10.30.6.0/23**(計 1016)。解説: 512 + 256 + 128 + 64 + 32 + 32 + 4 + 4 = 1032、2048 − 1032 = 1016
- 例題 2: 「親 `192.168.40.0/23`。開発 120、営業 60、総務 25、サーバー 12、リンク 1 本。未使用は 3 ブロック。」→ **192.168.40.0/25、.40.128/26、.40.192/27、.40.224/28、.40.240/30** / 未使用 **192.168.40.244/30、192.168.40.248/29、192.168.41.0/24**(計 268)

## 3. レベル 31〜40: アドレスの種別と到達性の規則

段の定義: プライベート/グローバル/ループバック/リンクローカル(APIPA)/マルチキャスト/文書用の範囲判定、IPv6 の GUA/ULA/LLA/マルチキャスト(`ff02::1`・`ff02::2`)/未指定、EUI-64、特殊アドレスを宛先にしたときの挙動。解答は入力(種別名・生成したアドレス)+ 4 択(挙動)。生成は計算生成(範囲判定・EUI-64)+ テンプレート+乱数(FactBank)。

### 3.1 FactBank(`server/questions/data/facts/`)

### 3.3 各レベルの詳細

#### Lv31 IPv4 の種別判定
- 生成: 種別 id を選び、その範囲内のアドレスを乱数で(グローバルは文書用でない範囲を避けられないので、**グローバルの例は 3 つの文書用範囲以外を本文に出さない**。グローバルを正解にする問題は作らず、選択肢・語彙としてのみ使う。第 9 章 8)。境界(172.15.255.255 / 172.32.0.0 / 192.169.0.0 / 169.253.255.255 / 223.255.255.255 / 240.0.0.0)の内外を 1/4 で混ぜる
- 入力の語彙: `term` で `v4-ranges.json` の表示名と別名(`APIPA`、`link-local`、`private`、`ループバック`、`loopback`、`マルチキャスト`、`multicast`、`文書用`、`TEST-NET`)を受ける
- 誤答(4 択時): 他の種別名 3 つ(「グローバル」を必ず 1 つ含める)
- 検証: 1 万件。範囲表を**別の表現(開始・終了の整数)**で持ち、整数比較で判定して一致。境界 ±1 の全数テスト
- 例題 1: 「`169.254.73.12` の種別は?」→ **リンクローカル(APIPA)**。解説: 169.254.0.0/16。DHCP で取得できなかったときに自動で付く
- 例題 2: 「`203.0.113.45` の種別は?」→ **文書用**。解説: 203.0.113.0/24 は例示専用(TEST-NET-3)

#### Lv32 IPv4 特殊アドレスの挙動(固定テンプレート)
- テンプレート: 「宛先が `{addr}` のパケットをホストが送ると、どうなるか」「送信元 `{addr}` が正しく使われるのはどんなときか」。`{addr}` は種別行の範囲内から seed で生成(文書用・プライベートは「インターネットの経路」の文脈)
- 誤答: 同じ表の別行の挙動文。「ルータが転送する」の有無で対立する文を 1 つ必ず含む
- 検証: 表の行ごとに人が一度確認(固定の方式)。誤答 3 つが正解行の挙動文と異なることをテスト。全文型 × 全行の全数描画で安全リンタを通す
- 例題 1: 「宛先 `255.255.255.255` のパケットは?」→ **同一リンクの全ホストに届き、ルータは転送しない**。誤答: 「ルータが他のネットワークへ転送する」「送信元ホスト自身にだけ届く」「経路がないので送信元に ICMP が返る」
- 例題 2: 「送信元 `0.0.0.0` を使うのは?」→ **まだ自分のアドレスを持たないホストが送るとき(DHCP の DISCOVER など)**。誤答: 「ルータが他のルータへ経路を広告するとき」「全ホストに届けたいとき」「自分自身へ送るとき」

#### Lv33 IPv6 の特殊アドレスとスコープ
- 生成: `::`、`::1`、`ff02::1`、`ff02::2`、`ff02::1:ffxx:xxxx`(下位 24 ビット乱数)、`ff05::…`/`ff0e::…`(スコープを問う)。Lv6 の 4 種は正解にしない(語彙としては残す)
- 誤答: 「全ノード」↔「全ルータ」、「ループバック」↔「未指定」、スコープ値の隣(ff02 ↔ ff05)
- 検証: 1 万件。プレフィックス照合の別実装(BigInt)。ソリシテッドノードは ff02::1:ff00:0/104 の照合
- 例題 1: 「`ff02::2` は?」→ **リンクローカルスコープの全ルータ宛マルチキャスト**。解説: ff02 はリンクスコープ、::1 が全ノード、::2 が全ルータ
- 例題 2: 「`ff02::1:ff7a:3b2c` は?」→ **ソリシテッドノードマルチキャスト**。解説: ff02::1:ff の後ろに対象アドレスの下位 24 ビット(7a:3b2c)が続く形

#### Lv34 修正 EUI-64 のインターフェース ID
- 生成: MAC を 1 つ(文書用 `00:00:5e:00:53:xx` → 反転 0→1 の例、ローカル管理 → 1→0 の例)。答えは下位 64 ビットを 4 ヘクステット(RFC 5952 の省略で正規化)
- 誤答: 反転忘れ(`0000:5eff:…`)、反転するビットの取り違え(0x01 → `0100:…`、0x80 → `8000:…`)、ff:fe を末尾に付けた値、fe:ff の順
- 検証: 1 万件。別実装: MAC を 2 進文字列にし、7 ビット目を文字置換で反転、24 ビット目の後ろに `1111111111111110` を挿入 → 16 進へ。両方向(Lv35)の往復で元に戻ることも assert
- 例題 1: 「MAC `00:00:5e:00:53:7a` から作る修正 EUI-64 のインターフェース ID は?」→ **200:5eff:fe00:537a**(`0200:5eff:fe00:537a` も同値)。解説: 00:00:5e | 00:53:7a の間に ff:fe を入れ、先頭バイト 00 の 7 ビット目(0x02)を反転して 02
- 例題 2: 「MAC `02:4c:9a:1e:77:03`」→ **4c:9aff:fe1e:7703**。解説: 先頭 02 → 00(ローカル管理ビットが 1 なので反転すると 0)。先頭ヘクステット 004c は 4c と省略

#### Lv35 EUI-64 の往復
- 生成: (a) `2001:db8:xxxx:xxxx::/64` + MAC → 完全アドレス。(b) EUI-64 形式のアドレス → 元の MAC。半々
- 誤答: (a) Lv34 の誤答を結合した値。(b) 反転を戻さない MAC、ff:fe を残した 8 バイトの値
- 検証: 1 万件。Lv34 の別実装 + 逆変換。(b) の生成アドレスは**必ず `ff:fe` を 25〜40 ビット目に含む**ことを assert(EUI-64 形式でないアドレスを出さない)
- 例題 1: 「プレフィックス `2001:db8:a1:4::/64`、MAC `00:00:5e:00:53:c1`。EUI-64 で作る完全なアドレスは?」→ **2001:db8:a1:4:200:5eff:fe00:53c1**
- 例題 2: 「`2001:db8:7:0:a8f3:21ff:fe4d:9c10` は EUI-64 で作られた。元の MAC は?」→ **aa:f3:21:4d:9c:10**。解説: ff:fe を取り除き a8 f3 21 4d 9c 10。先頭 a8 = 1010 1000 の 7 ビット目を戻すと aa

#### Lv36 リンクローカルとソリシテッドノード
- 2 欄: MAC → `fe80::` + EUI-64、そのアドレス(または与えた GUA)→ ソリシテッドノードマルチキャスト
- 誤答: `fe80:0:0:1::`(間違ったプレフィックス長)、ff02::1:ff の後ろに下位 32 ビット、下位 16 ビット
- 検証: 1 万件。別実装(Lv34 + 下位 24 ビットの文字列切り出し)
- 例題 1: 「MAC `00:00:5e:00:53:1f` のホストのリンクローカルアドレス(EUI-64)と、そのソリシテッドノードマルチキャストアドレス。」→ **fe80::200:5eff:fe00:531f** / **ff02::1:ff00:531f**
- 例題 2: 「GUA `2001:db8:1:2:3c4d:5eff:fe6f:7a8b` に対応するソリシテッドノードマルチキャストアドレス。」→ **ff02::1:ff6f:7a8b**。解説: 下位 24 ビット = 6f:7a8b

#### Lv37 IPv6 特殊アドレスの挙動(固定テンプレート)
- テンプレート: Lv32 と同じ 2 文型 × `v6-special.json` の 6 行(fe80、ff02::1、::、::1、fd00、2001:db8)
- 例題 1: 「宛先 `fe80::1` のパケットは?」→ **同一リンクの中だけで届き、ルータは別のリンクへ転送しない**。誤答: 「ルータが宛先のリンクまで転送する」「全ノードに届く」「送信元に戻る」
- 例題 2: 「送信元 `::` を使うのは?」→ **まだ送信元アドレスを持たないとき(重複アドレス検出の最中など)。宛先には使えない**。誤答: 「ループバックで自分に送るとき」「全ルータに届けたいとき」「どんな宛先にも使える」

#### Lv38 境界すれすれの範囲判定(4 択)
- 生成: 種別 1 つを選び、範囲内 3 つ + 範囲外側 1 つ(境界 ±1〜±255)で「〜でないものは」。または範囲外 3 + 範囲内 1 で「〜であるものは」
- 検証: 4 択の 3 つが同じ種別、1 つが別種別であることを範囲表の別実装で assert。選択肢の重複なし
- 例題 1: 「プライベートアドレスで**ない**ものは?」選択肢 `10.255.255.254` / `172.31.255.1` / `192.168.255.254` / `172.32.0.1` → **172.32.0.1**。解説: 172.16.0.0/12 は 172.16〜172.31 まで
- 例題 2: 「リンクローカル(APIPA)で**ない**ものは?」`169.254.0.1` / `169.254.255.254` / `169.253.255.255` / `169.254.128.0` → **169.253.255.255**

#### Lv39 複数アドレスの転送可否
- 本文: 「組織内のルータ R1 は、次の宛先のパケットを別のインターフェースへ転送するか。○×で。」3〜4 欄
- 生成: v4・v6 を混ぜ、転送する(プライベート・GUA・ULA)と転送しない(fe80・ff02::1・169.254・127・224.0.0.x・255.255.255.255)を少なくとも 1 つずつ
- 検証: FactBank の真偽と別実装(範囲表 → 真偽)の一致。欄ごとに assert
- 例題 1: (a) `fe80::1` (b) `2001:db8::10` (c) `ff02::1` → **× / ○ / ×**
- 例題 2: (a) `10.5.5.5` (b) `169.254.10.1` (c) `224.0.0.5` (d) `127.0.0.1` → **○ / × / × / ×**

#### Lv40 総合: ホストのアドレス一覧を読む
- 表(`table`): 1 台のホストが持つアドレス 3〜5 個(fe80 EUI-64、GUA EUI-64、ULA、IPv4 プライベート、APIPA のうち)。欄: (a) 元の MAC、(b) インターネット上の宛先に送信元として使えるアドレス、(c) ルータを越えないアドレス。4 択 1 つ(例: 169.254 が付いている理由)
- 生成: EUI-64 系はすべて同じ MAC から作る(一貫性)。IPv4 は 1 つだけ
- 検証: 各欄を Lv31〜36 の別実装で再計算。(b) が一意(GUA が 1 つだけ)であることを assert
- 例題 1: PC1 の一覧 `fe80::200:5eff:fe00:5342/64`、`2001:db8:10:1:200:5eff:fe00:5342/64`、`fd12:3456:789a:1:200:5eff:fe00:5342/64`、`192.168.1.20/24` → (a) **00:00:5e:00:53:42** (b) **2001:db8:10:1:200:5eff:fe00:5342** (c) **fe80::200:5eff:fe00:5342**
- 例題 2: PC2 の一覧 `169.254.44.7/16`、`fe80::a8f3:21ff:fe4d:9c10/64`、`10.3.9.15/24` → (a) **aa:f3:21:4d:9c:10** (b) IPv4 で別サブネットへ送る送信元に使えるのは **10.3.9.15** (c) 4 択「169.254.44.7 が付いている理由」→ **DHCP でアドレスを取得できず自動構成された**

## 4. レベル 41〜50: 層をまたぐカプセル化の追跡

段の定義: 同一/異サブネットの通信で各ホップの送信元/宛先 MAC と IP がどう変わるか、ルータでの再カプセル化と TTL の減少、OSI/TCP-IP の層と機器の分担。ARP 表・MAC 表は収束済みのものを与える。解答は表の読み解き + 入力。生成はシナリオ生成器(NetGen で 2〜4 ホップ、シミュレータが各ホップのヘッダを計算)。検証はシミュレータと独立の手書き規則。

LEVELS.md 第 7 章 #3 の決定により**伝送の計算(帯域と転送時間、伝搬遅延)をこの段に吸収**する。「ホップごとに遅延が積み上がる」として 46〜47 に置く。

### 4.1 トポロジの表現(図 UI は帯 C 以降なので**表**で渡す)

| 機器 | IF | IP アドレス | MAC アドレス | 接続先 |
|---|---|---|---|---|
| PC1 | Eth0 | 10.1.1.10/24(GW 10.1.1.1) | 02:00:00:00:00:1a | SW1 Gi1/0/1 |
| R1 | Gi0/0 | 10.1.1.1/24 | 02:00:00:00:a1:00 | SW1 Gi1/0/24 |
| R1 | Gi0/1 | 10.1.2.1/24 | 02:00:00:00:a1:01 | SW2 Gi1/0/24 |

### 4.3 生成器(`hops.js`)とシミュレータの最小版

- **NetGen 最小版(#9)**: 直列トポロジだけ。ホスト 2〜3 台(同一サブネットの PC3 を 1/3 で足す)、ルータ 1〜3 台、スイッチは各 LAN に 1 台。アドレスは拠点の `10.x.0.0/16` の中から /24(LAN)と /30(ルータ間)。MAC はローカル管理の `02:…`。各 LAN のスイッチに MAC 表(収束済み)、各ホストとルータ IF に ARP 表(収束済み)を作る
- **シミュレータ最小版(#10)**: `forward(topology, srcHost, dstHost, initialTtl)` が区間ごとの `{ srcMac, dstMac, srcIp, dstIp, ttl, outPort }` の配列を返す純関数。規則: 送信機器の出口 IF の MAC が送信元 MAC。宛先 IP が出口 IF と同一サブネットなら宛先ホストの MAC、違えば次ホップ(ホストなら GW、ルータなら静的経路の次ホップ)の MAC。IP は不変。ルータを出るたび TTL −1
- **検証器(別実装)**: 区間ごとに「この区間の両端は何か」を手で列挙した規則表(ホスト→GW、R_i→R_{i+1}、最終ルータ→宛先ホスト)から MAC と TTL を組み立て、シミュレータの配列と一致を確認。1 万件。復路は src/dst を入れ替えて同じ検査。`outPort` は MAC 表を線形走査して突き合わせ
- **誤答(暫定 4 択用)**: 宛先 MAC に最終宛先ホストの MAC(ゲートウェイを忘れる)、宛先 IP にゲートウェイの IP(IP を書き換えると思う)、送信元 MAC を変えない(ルータ通過後も PC1 の MAC)、TTL を減らさない/ 2 減らす、ルータの反対側 IF の MAC

### 4.4 各レベルの詳細

#### Lv41 層と機器・PDU・アドレスの分担(固定テンプレート)
- FactBank `layers.json`: 機器(ハブ・スイッチ・ルータ・L3 スイッチ・ホストのアプリ)× 層(L1〜L4、L7)× PDU(ビット・フレーム・パケット・セグメント)× 見るアドレス(なし・MAC・IP・ポート)× 書き換えるもの(なし・なし・L2 ヘッダと TTL・同・—)。文型: 「X を見て転送先を決める機器は」「ルータが書き換えるのは」「第 n 層の PDU は」
- 検証: 表を人が確認。誤答は同じ列の別行。全文型 × 全行で重複なし
- 例題 1: 「宛先 MAC アドレスを見て出力ポートを決める機器は?」→ **スイッチ(第 2 層)**。誤答: ハブ(第 1 層)/ ルータ(第 3 層)/ ロードバランサ(第 7 層)
- 例題 2: 「ルータがパケットを別のネットワークへ転送するとき、書き換えるものは?」→ **送信元・宛先 MAC アドレスを付け替え、TTL を 1 減らす(IP アドレスは変えない)**。誤答: 「送信元 IP をルータの IP に書き換える」「宛先 IP を次のルータの IP に書き換える」「何も書き換えない」

#### Lv42 区間 1(ホスト → ルータ)のヘッダ
- 4 欄: 送信元 MAC、宛先 MAC、送信元 IP、宛先 IP。異サブネット 2/3、同一サブネット(PC1 → PC3。宛先 MAC が PC3 のもの)1/3
- 例題 1(4.1 の表): 「PC1 が PC2(10.1.2.20)へ送る区間 1(PC1 → R1)のフレームの 4 項目。」→ **02:00:00:00:00:1a** / **02:00:00:00:a1:00** / **10.1.1.10** / **10.1.2.20**。解説: 宛先が別サブネットなので宛先 MAC はゲートウェイ R1 Gi0/0。IP は最終宛先のまま
- 例題 2: 「PC1 が同じサブネットの PC3(10.1.1.30、MAC 02:00:00:00:00:3c)へ送る区間 1。」→ **02:00:00:00:00:1a** / **02:00:00:00:00:3c** / **10.1.1.10** / **10.1.1.30**。解説: 同一サブネットなのでゲートウェイを通らず、宛先 MAC は PC3 のもの

#### Lv43 区間 2(ルータ → ホスト)のヘッダと TTL
- 5 欄: 4 項目 + 区間 2 の TTL(初期 TTL を表に明記)
- 例題 1(4.1 の表、PC1 初期 TTL 64): 「区間 2(R1 → PC2)。」→ **02:00:00:00:a1:01** / **02:00:00:00:00:2b** / **10.1.1.10** / **10.1.2.20** / **63**。解説: R1 は Gi0/1 の MAC を送信元に、PC2 の MAC を宛先に付け替える。IP は不変、TTL は 64 → 63
- 例題 2: 初期 TTL 128 の PC2 から PC1 への区間 2(R1 → PC1)→ **02:00:00:00:a1:00** / **02:00:00:00:00:1a** / **10.1.2.20** / **10.1.1.10** / **127**

#### Lv44 2 ルータ・指定区間のヘッダ
- R1 Gi0/1 10.0.12.1/30(MAC …:a1:01)— R2 Gi0/0 10.0.12.2/30(MAC …:a2:00)、R2 Gi0/1 10.1.2.1/24(MAC …:a2:01)
- 例題 1: 「PC1(TTL 64)→ PC2 の区間 2(R1 → R2)。」→ **02:00:00:00:a1:01** / **02:00:00:00:a2:00** / **10.1.1.10** / **10.1.2.20** / **63**
- 例題 2: 「区間 3(R2 → PC2)。」→ **02:00:00:00:a2:01** / **02:00:00:00:00:2b** / **10.1.1.10** / **10.1.2.20** / **62**

#### Lv45 3 ルータ・復路の区間
- PC2(初期 TTL 128)の応答。復路の区間 1 = PC2 → R3、区間 4 = R1 → PC1
- 例題 1: 「PC2 → PC1 の応答、復路の区間 1。」→ 送信元 MAC **PC2** / 宛先 MAC **R3 の LAN 側 IF** / **10.1.2.20** / **10.1.1.10** / **128**
- 例題 2: 「復路の区間 4(R1 → PC1)の TTL。」→ **125**。解説: 128 − 3(R3、R2、R1 を通過)

#### Lv46 直列化遅延(送出時間)
- 本文に単位規約を明記: 「1 MB = 1,000,000 バイト、1 Mbit/s = 1,000,000 ビット/秒、答えは **{単位}** で整数」。パラメータは答えが指定単位で整数になる組だけを採用(生成器が割り切れるかを確認して引き直す)
- 誤答: バイト→ビットの ×8 忘れ(1/8)、×8 を 2 回(8 倍)、単位の 1000 倍ずれ
- 検証: 1 万件。別実装(BigInt でビット数 ÷ 帯域)。整数性を assert
- 例題 1: 「1,500 バイトのフレームを 100 Mbit/s のリンクに送り出す時間は?(マイクロ秒)」→ **120**。解説: 1500 × 8 = 12,000 ビット ÷ 100,000,000 = 0.00012 秒
- 例題 2: 「25 MB のファイルを 20 Mbit/s で送る時間は?(秒。ヘッダなど他の要素は無視)」→ **10**。解説: 25,000,000 × 8 = 200,000,000 ビット ÷ 20,000,000 = 10 秒

#### Lv47 伝搬遅延とホップごとの積み上げ
- 規約を明記: 伝搬速度 2 × 10^8 m/s、ストアアンドフォワード(各ルータはパケット全体を受け取ってから次へ送る)、処理遅延と待ち時間は 0。答えはミリ秒またはマイクロ秒で整数か小数 1 桁(生成器が揃える)
- 誤答: 伝搬だけ・直列化だけ、直列化を 1 回しか数えない、距離を km のまま割る
- 検証: 1 万件。別実装: Σ(直列化_i + 伝搬_i)。小数は 1/10 ミリ秒の整数として比較(浮動小数の誤差を避ける)
- 例題 1: 「1,000 バイトのパケットを 10 Mbit/s、長さ 2,000 km のリンク 1 本で送る。宛先が受け取り終わるまでの時間は?(ミリ秒)」→ **10.8**。解説: 直列化 8,000 ÷ 10,000,000 = 0.8 ms、伝搬 2,000,000 m ÷ 2×10^8 = 10 ms
- 例題 2: 「1,500 バイト、各リンク 100 Mbit/s・200 km、ルータ 2 台(リンク 3 本)、ストアアンドフォワード。」→ **3.36**(ミリ秒)。解説: 直列化 120 µs × 3 + 伝搬 1 ms × 3 = 0.36 + 3 = 3.36 ms

#### Lv48 ARP 表 + MAC 表の 2 表合成
- 表 2〜3 個(トポロジ表、PC1 の ARP 表、SW1 の MAC 表)。欄: 「区間 1 で SW1 がフレームを出すポート」。異サブネット宛なので ARP 表から GW の MAC を取り、MAC 表でそのポートを引く(PC2 の MAC を MAC 表で探すと**載っていない**ようにしてひっかけにする)
- 誤答: 宛先 PC の MAC を引いたポート(SW1 の表に無いので「全ポート」)、送信元 PC のポート、ルータの反対側 IF
- 検証: 別実装(ARP 表の線形走査 → MAC 表の線形走査)。MAC 表に宛先 PC の MAC が**無い**ことを assert(同一サブネット問題のときは有る)
- 例題 1: SW1 の MAC 表 `02:00:00:00:00:1a → Gi1/0/1`、`02:00:00:00:00:3c → Gi1/0/2`、`02:00:00:00:a1:00 → Gi1/0/24`。「PC1 → PC2(別サブネット)の区間 1 で SW1 が出すポート。」→ **Gi1/0/24**
- 例題 2: 「PC1 → PC3(同一サブネット)で SW1 が出すポート。」→ **Gi1/0/2**

#### Lv49 全区間の表を埋める
- 2 ルータ 3 区間 × (送信元 MAC、宛先 MAC、TTL)の 9 欄。IP は不変なので問わない(本文で「IP は全区間で同じ」と示し、変わるもの/変わらないものの対比を解説で述べる)
- 例題 1(Lv44 の構成、PC1 TTL 64): 区間 1 **PC1 / R1 Gi0/0 / 64**、区間 2 **R1 Gi0/1 / R2 Gi0/0 / 63**、区間 3 **R2 Gi0/1 / PC2 / 62**
- 例題 2: 同構成で PC2(TTL 128)→ PC1: 区間 1 **PC2 / R2 Gi0/1 / 128**、区間 2 **R2 Gi0/0 / R1 Gi0/1 / 127**、区間 3 **R1 Gi0/0 / PC1 / 126**

#### Lv50 総合: 往復と TTL
- 3 ルータ。欄: 往路の区間 k の送信元/宛先 MAC、復路の区間 m の送信元/宛先 MAC、PC2 到着時の TTL、PC1 に戻った応答の TTL
- 例題 1: PC1(64)→ PC2(128)。往路区間 2(R1 → R2)、復路区間 3(R2 → R1)。→ 往路 **R1 Gi0/1 / R2 Gi0/0**、復路 **R2 Gi0/0 / R1 Gi0/1**、到着 TTL **61**、応答到着 TTL **125**
- 例題 2: 往路区間 4(R3 → PC2)、復路区間 1(PC2 → R3)。→ 往路 **R3 LAN IF / PC2**、復路 **PC2 / R3 LAN IF**、**61** / **125**

## 9. 判断に迷った点(ユーザーに決めてもらうこと)

1. **入力式ができるまでの暫定配信**: #1・#2 の実装前は Lv11 以上を (a) いまどおり Lv10 相当で出す、(b) 本書の「誤答の作り方」を使って同じ題材を 4 択で出す(知識は同じ、形式だけ暫定)。(b) なら各レベルの誤答設計をそのまま使える。LEVELS.md の「解答の形は知識に従う」に照らすと (b) は一時的な妥協
2. **複数欄の答えの形**(0.2 の `fields` / `compare`): #1 の共通形式の一部になる。欄ごとの部分正解を認めず「全欄一致で正解 1 回」としたが、欄が 9 つの Lv49・50 では厳しい。欄数を 6 までに抑えるか、全欄一致を貫くか
3. **N 番目の数え方**: 1 始まりで統一し本文に毎回明記する案を採った(0 始まりは「サブネット 0」の慣習と混ざるため)。0 始まりを受け付けるかどうか(受け付けない案)
4. **/31(RFC 3021)の扱い**: 使用可能範囲・点対点リンクでは使わず、/30 までとした。/31 を「2 台のリンクに使える」として教えるかどうか
5. **種別名の入力(Lv31・33)**: LEVELS.md は入力だが、語彙の表記ゆれが多い。`term` の別名表で受ける案と、4 択に落とす案。別名表で受けるなら Tab 補完(語彙だけ)を入力欄に付けてよいか
6. **文書用 MAC `00:00:5e:00:53:xx` の採用**: ローカル管理 MAC だけだと EUI-64 の反転が常に 1 → 0 になる。RFC 7042 の文書用範囲を使えば 0 → 1 の例も安全に作れる。採用の可否(採用するなら `banned.json` / 安全リンタの許可範囲に加える)
7. **伝送の計算の規約**(Lv46・47): 1 MB = 10^6 バイト(2^20 ではない)、伝搬速度 2 × 10^8 m/s、ストアアンドフォワード、処理・待ち時間 0。本文に毎回明記する前提でこの値にしたが、変える余地
8. **範囲表の網羅**: 共有アドレス空間 `100.64.0.0/10`、ディレクテッドブロードキャスト、`0.0.0.0/8`、`240.0.0.0/4` は迷いやすいので外した。また「グローバル」を正解にする問題は、本文に実在の範囲を出さないため作らない(語彙・誤答としてのみ)。加えるか
9. **基数変換を単体のレベルにすること**(Lv11・12): 段の定義では「計算の一部として含む」だが、段の中の 10 レベルを「量と段数を少しずつ増やす」ために最初の 2 レベルを変換単体にした。不要なら 11〜12 を 14〜15 に吸収して空いた 2 レベルで「所属番号 + 範囲」の段数増しを入れる
10. **初期 TTL を表に明記する方針**(41〜50): OS ごとの既定値(64/128/255)を知識にしない。明記で良いか
11. **Lv21 と Lv4 の近さ**: Lv21 は Lv4 を 3 区画同時にしただけに見える。区画のプレフィックスではなく「大きい順の並べ替え」を問うとして残したが、22 と統合して空いた 1 レベルを 26〜27 の間(「2 の冪でないホスト数の切り上げの罠」)に使う案もある
12. **11〜30 の供給**: 純計算なので**その場生成**で問題なく動く(Lv1〜10 と同じ)。8.13 の「固定問題は拠点に紐づき、クリアまで同じ問題」を 11〜30 にも適用するか(適用すると、同じ拠点に挑み直すとき同じ数値が出る。学習上は固定の方が「解き直し」になる)
13. **VLSM の同サイズ区画の入替許容**: 集合比較で許したが、画面で区画名ごとに欄を出すと「営業の欄に支店の CIDR を書いた」が正解になり違和感がある。欄のラベルを「大きい方から 1 番目・2 番目 …」にして区画名を併記する案
14. **defenseNote の定型化**(0.7): 計算問題で「守る側」の注記を段ごとの定型 + パラメータ差し込みにした。攻守同重の趣旨に足りるか、もしくは Lv11〜40 では省略可とするか
15. **LEVELS.md の 11〜20 の表記**: 段の定義にある「/9〜/30」は Lv14・15 でそのまま使い、Lv16〜18 の分割では p2 ≤ 30 で止めた。/9〜/12 のような大きな親(1600 万アドレス)の N 番目は数が大きくなるので、本文に「分割数も答えよ」を付けて計算の手がかりにした。親の下限を /8 まで広げるか
