# レベル定義(Lv1〜999): ネットワーク知識の階段

> **2026-10-23 ユーザー決定**: レベルは 1〜100 にまとめる(90〜100 は神レベル)。学ぶ順の一覧は `docs/LEVEL-LIST.md` 第 12 章。この文書の 1〜999 の階段は、問いの型の参考として残す(置き換え中)。

作成: 2026-10-14 / 全面改訂: 2026-10-17(帯=操作方式 から 領域=知識 へ組み替え)

このファイルは「レベル 1〜999 で何を問うか」の設計書。実装の順番はフェーズ計画(`DESIGN.md` 第 8 章)に従う。
旧版(操作方式で切った帯 A〜I)は Git の履歴にある。旧版の帯記号を参照している箇所は、本版の 100 刻みの領域番号に読み替える。

## 1. 原則(2026-10-17 ユーザー決定)

1. **レベルは、問われるネットワークの知識の難しさだけで決める。** 制限時間・2 問連続・資源予算・情報を伏せる、といった小細工でレベルを変えない(`DESIGN.md` 8.18)。高レベルの「観測から推論する」題材は、現実の診断でも情報が全部は揃わないので、知識の課題として扱う(伏せること自体を難しさにしない)
2. **1 レベル = 1 つの知識の単位。** 10 レベルごとに 1 段(セグメント)とし、段ごとに「問いの型 + 扱う概念 + 計算や読解の段数」と「前の段より難しい理由」を書く。段の中の 10 レベルは、同じ知識の単位で扱う量と段数を少しずつ増やす(例: 行数、条件の数、拠点数)
3. **100 ごとに知識の領域を変える**(第 2 章の表)。拠点の形の体系(`public/shapes.js`、`DESIGN.md` 8.8)では 100 の位が外枠の種類なので、外枠を見れば知識の領域がわかる
4. **解答の形は知識に従う。** 計算は 4 択か入力、表の読み解きは入力、コマンドの知識は模擬ターミナルで手で打つ、設定の知識は設定を書いて意味で判定する。方式を難易度の理由にしない
5. **突破は常に正解 1 回**(8.12)。固定問題は拠点に紐づき、クリアか定期更新まで同じ問題が残る(8.13)
6. **各段に自動生成の方式と検証の方法を付ける**(第 5 章)。答えの正しさはシミュレータと別実装の解き直しで保証する
7. **安全(`DESIGN.md` 3.5)**: すべて架空ネットワーク。攻撃手法の名前・手順・ツールの用法・検知回避・マルウェアは、どの領域の本文・解説・誤答にも入れない。高レベル帯の「攻略」は、架空の構成とゲーム内のルールを読み解くパズルとしてだけ書く

## 3. 地図との接続(2026-10-17 決定)

- **出題レベル = 拠点の基礎レベル + 強化の段数**(`world.js` の `levelFor`)。**強化に上限を設けない**: 所有者が正解を重ねるほど拠点のレベルが上がり、攻める側はその分難しい知識を問われる。これにより、東京の駅(基礎 Lv1〜5)から始めても、守りが育てば Lv50、Lv100 の問題が自然に出る(現状の上限 3 段は撤廃する。実装は手順 4 とあわせて)
- 強化の問題は「いまの出題レベル」の問題。つまり自分の拠点を Lv30 に育てるには Lv30 の知識が要る
- 地図の階層(2026-10-18 決定): 拠点があるのは区・市の段(駅・名所・町・字)だけ。**都道府県・国などの地域は拠点ではなく配下の拠点の集まり**で、基礎レベルは置かない(国 777 などは廃止)。Lv11 以上の問題は、強化で育った拠点と固定問題で出る。強化段数は 1 日ごとに 1 下がる(DESIGN.md 3.2)
- **拠点の基礎レベル(2026-10-19 決定。`LEVEL-PLAN.md`)**: 町・字 1〜9、ふつうの駅 10、名所 15〜70、観光地 15〜300、乗り換え駅・港 30〜99、空港 150〜500、主要駅 200、城・塔 300、都道府県庁舎 400、東京都庁 600、国会議事堂 777。**問題のあるレベルの拠点だけ占領・強化できる**(生成器の無いレベルは、線はつながっていても問題が出ない。強化も、上げた先に問題があるときだけ)
- スポンサー拠点(8.16)は乗っ取り不可。購入額で初期レベルが決まる優遇はあってよい

## 4. 各領域の階段(10 段 × 10 領域)

各領域は担当エージェントが起案し、横断審査(重複・順序・原則違反・安全・生成可能性)を経て修正したもの。各節末尾の「審査メモ」は修正の記録。

### 1〜99 アドレッシングと基礎

IPv4/IPv6 のアドレスがどう決まり(サブネット・プレフィックス)、どう区別され(種別・範囲)、どう運ばれ(L2/L3 のカプセル化・最長一致)、どう付け替えられ(NAT)、どう配られて名前に結びつくか(DHCP・DNS)までを扱う。1〜10(DESIGN.md 8.18 訂正版)はそのまま起点にし、11〜99 を続ける。難しさの軸は **「1 つの式・1 つの表で決まる値を選ぶ → 複数段の計算を自分で組み立てる → 要件から設計する → 範囲の知識と挙動の規則を組み合わせる → 層をまたいで追跡する → 複数の表・規則を合成する → 観測から原因を逆算する」** の一方向。制限時間・2 問連続・情報の伏せ方は使わない(8.18)。解答の形は知識に従って決める(値を自分で作る知識は入力、規則の帰結を問う知識は 4 択、表から読む知識は表の読み解き + 入力)。供給(その場生成か DB か)は 8.6 / 8.13 に従い、ここでは決めない。安全(3.5 / LEVELS.md 2.11 末尾): アドレスは内側 `10/8`・`172.16/12`・`192.168/16`・`fd00::/8`・`fe80::/10`、外側は文書用 `192.0.2.0/24`・`198.51.100.0/24`・`203.0.113.0/24`・`2001:db8::/32` に固定し、ホスト名はゲーム内専用の接尾辞、機器名・組織名は架空。安全リンタを全段の本文・解説に通す。入力式の判定器は表記の揺れ(先頭 0、全角数字、IPv6 の省略形の同値、大文字小文字)を正規化してから比較し、その正規化自体をテストする。

### 100〜199 L2・L3 の動作

1〜99 で「アドレスのどこまでがネットワークか」を身につけた後、この領域では **そのアドレスを持つフレームとパケットが、スイッチとルータをどう通るか** を扱う。L2(MAC アドレステーブル、ARP、VLAN/トランク、STP)と L3(経路表の最長一致、TTL、MTU とフラグメント、ICMP)を、1 台・1 表の静的な読み取りから始め、2 層の連結(ARP の相手はサブネット判定で決まる)、複数機器にまたがる条件の照合(VLAN)と最適化の計算(STP)、数値計算(TTL/MTU)、観測からの逆算(ping/traceroute)、ヘッダの旅(カプセル化がどこで変わるか)、最後に自分でコマンドを選んで観測を集める総合切り分けまで上げる。難しさの軸は 3 つ。(1) 関わる機器と表の数(1 → 複数)、(2) 推論の段数(1 段の読み取り → 3〜5 段の連鎖)、(3) 観測を選ぶ知識(表を与える → どのコマンドの出力が候補を絞るかを自分で判断して模擬ターミナルで取る。情報を伏せるのではなく、必ずコマンドで取れる)。解答の形はその知識に自然な形(表を読むなら入力、観測なら模擬ターミナル)で決め、難易度の道具にはしない。供給は 8.6 / 8.13 どおり seed 付きで生成して DB に保存し、拠点×レベルに紐づけてクリアで差し替える。多段の問題(160 以降)は途中経過(打ったコマンド)を保存する。すべて拠点の架空ネットワーク(10.x.0.0/16。外側は 192.0.2.0/24 などの文書用範囲)で行い、MAC アドレスはローカル管理アドレス(第 2 桁が 2/6/A/E)だけを生成して実在ベンダーの識別子を避ける。コマンドは到達確認(ping、tracert/traceroute)と自機・機器の表の表示(arp -a / ip neigh、ip route / route print、show mac address-table、show vlan、show spanning-tree、show ip route、show ip interface brief 相当)に限り、走査系は扱わない。

### 200〜299 サービスのしくみ

ネットワークの上で動くサービス(DNS、DHCP、NAT/NAPT、HTTP、TLS と証明書、メール、NTP、SNMP、syslog)が「どの順番で何をやりとりし、どの規則で結果が決まるか」を問う領域。アドレッシング(1〜99)と L2/L3 の転送(100〜199)ができる前提で、パケットが届いたあとにサービスが何をするかを扱う。難しさの軸は **たどる段数と突き合わせる情報源の数** だけで上げる: 1 つの照合(役割とポート) → 1 回の交換の順序(DHCP) → 表・ゾーンを 1 段読む(DNS) → 複数レコードを数段たどる(CNAME・委任) → 両方向の書き換えを計算する(NAT/NAPT) → 1 本の接続の状態と規則を順に当てる(HTTP、TLS) → 複数ホップ・複数ドメインの記録を突き合わせて判定する(メール、SPF/DKIM/DMARC) → サービスをまたぐ因果を 1 つの根本原因に絞る(NTP・SNMP・syslog を観測の土台にした横断診断)。解答の形はその知識を問うのに自然な形を採り、制限時間・2 問連続・情報の伏せは使わない。すべてゲーム内の架空ネットワークで行う: 外側のアドレスは `192.0.2.0/24`・`198.51.100.0/24`・`203.0.113.0/24`・`2001:db8::/32`、内側は `10/8` 等、ドメインは文書用(example.jp 相当)かゲーム内専用の接尾辞、CA・メールサーバー・時刻源はすべて架空名。実在企業・実在アドレス・本物に使える攻撃手順は入れない。本帯は Lv5 以上なので供給は DB の固定問題(DESIGN.md 8.6 / 8.13): どの生成方式でも (テンプレート id, seed, 版) で生成して検証器を通し、本文・答え・判定方式のスナップショットを保存する。クライアントに答えは送らない。

### 300〜399 セキュリティの基礎と設定

守る側の知識だけを扱う領域。「何を守るか(CIA)→ 誰を通すか(認証・認可)→ どう守るか(暗号・証明書)→ どこで通す・止めるか(ACL、ゾーン、ステートフル検査、802.1X、VPN、WAF/IDS)→ 守れているかをどう確かめるか(ログ)」の順に並べる。難しさの軸は 3 つで、段が上がるほど **(1) 1 問で同時に扱う概念の数**(用語 1 つ → 鍵 2 種の組み合わせ → ACL の行×順序×方向 → ゾーン×状態×ログ)、**(2) 読む対象の段数**(事象 1 文 → 証明書チェーン 3 段 → ACL 3〜8 行 → 複数機器の経路上で評価される位置 → ポリシー表 + セッション表 + ログ)、**(3) 答えの決まり方**(表の値で決まる → 式で決まる → 判定器で再計算して決まる → 書いた設定が全テストケースを満たすかで決まる)が増える。制限時間・情報の伏せ方・解答方式は難易度の道具にしない。解答の形は知識に自然な形(用語なら 4 択・入力、ACL なら判定、要件なら設定を書く)を段ごとに決める。すべて架空ネットワーク(拠点の 10.x.0.0/16、外側は 192.0.2.0/24 等の文書用範囲、ホスト名はゲーム内接尾辞)で出す。ACL とポリシーはゲーム内の簡略文法で書き、実機の構文(400〜499)とは分ける。供給は 8.6 / 2.11 のとおり seed 付き生成 → 検証器 → DB 保存、クリアで差し替え。攻撃手法の名前・手順・ツールの用法・検知回避は、本文・解説・誤答のどこにも入れない(安全リンタ `banned.json` で機械検査)。

### 400〜499 ルーティングと機器設定

ルータ・スイッチ 1〜6 台の架空ネットワーク(拠点の 10.x.0.0/16 の中。外側は 192.0.2.0/24 などの文書用アドレス、AS 番号は 64512〜65534)を対象に、経路を作る側・機器を設定する側の知識を問う領域。100〜199 で「与えられた経路表や表を読む」ことは済んでいるので、ここでは要件から設定を書き、設定から収束後の状態(経路表・隣接・Active・クラス分け)を自分で求める。難しさの軸は 4 つで、段が上がるほど積み上がる: (1) 1 台の静的な設定 → 2 台間の整合条件 → 事象で遷移する状態、(2) ホップ数 → 帯域由来のコスト → 複合メトリック → 順序付きの属性比較、(3) 1 つのプロトコル → エリア境界で性質が変わる → 2 つのプロトコルの相互作用 → 人の方針を属性操作に翻訳する、(4) 問いに機能名が書かれている → 症状だけから機能を絞って誤設定を特定する。解答の形は知識に従う: 収束結果を問うなら経路表の読み解き・入力、構成を作る知識なら設定を書く(ゲーム内の簡略文法で書き、文字列一致ではなく、解析して模擬機に適用した結果が要件を満たすかで判定)、状態を見る知識なら模擬ターミナルで show を打つ。コマンドはすべて手で打つ。全段とも、架空の機器名・架空の網だけを使い、実在製品名は出さない(構文は資格試験で使う一般的な書き方に合わせる。DESIGN.md 3.4)。LEVELS.md 2.4 の経路・冗長化・管理面・QoS・差分、2.2 の OSPF/BGP の読み解き、2.5 のルーティングプロトコルの部分をこの領域に集める。

架空のクラウド「PC クラウド」で、仮想ネットワーク・権限・公開経路・接続・観測・設計を扱う。部品の名前は一般語(仮想ネットワーク、サブネット、セキュリティグループ、ネットワーク ACL、ルートテーブル、インターネットゲートウェイ、NAT ゲートウェイ、ロードバランサ、マネージド DNS、CDN、WAF、ピアリング、トランジットハブ、プライベートエンドポイント、サイト間 VPN、専用線接続、フローログ、リージョン/ゾーン)だけを使い、実在のサービス名・製品名・料金表は出さない。アドレスは 2.11 の範囲(内側 10/8・172.16/12・192.168/16、外側 192.0.2.0/24・198.51.100.0/24・203.0.113.0/24、AS 64512〜65534)、ホスト名はゲーム内専用の接尾辞に限り、安全リンタを通す。難しさの軸は「評価する層の数と境界の数」で上がる: **1 つの部品の規則を正しく評価する**(600〜639)→ **意味の違う層を順に通す追跡**(640〜659)→ **仮想ネットワークの境界・クラウドとオンプレの境界を越える**(660〜679)→ **設定ではなく観測から原因を逆算する**(680〜689)→ **障害とコストという相反する制約を同時に満たす設計**(690〜699)。解答の形は知識に従う: 値が 1 つに決まるものは入力、規則やログを読む段は読み解き(入力)、構成を作らせる段は設定を書いてシミュレータが到達性と権限を判定する。供給は 8.6 のとおり seed 付きで生成・検証して DB に置き、クリアで差し替える(8.13)。

### 700〜799 解析と診断

守る側・運用側の知識を問う領域。与えられるのは架空ネットワーク(拠点の 10.x.0.0/16 と文書用アドレス範囲。2.11 の安全面)のキャプチャ・ログ・設定・模擬ターミナルの出力で、そこから「何が・どこで・いつ・なぜ」起きたかを特定する。難しさは **読む資料の種類と量**(1 本のキャプチャ → 1 台の設定 → ツールの出力 2 種 → 観測点 2 か所 → ログ 1 種の統計 → ログ 1 種 + 許可一覧 → ログ 3〜4 種 → 設定 3〜6 台 + 図 + 台帳 → 全部)、**突き合わせる段数**(1 → 2 → 3 以上。NAT の対応表・時刻ずれ・構成図を介した間接の対応づけが加わる)、**原因の数**(1 つ → 複数の指摘 → 連鎖した 2〜3 要因)だけで上げる。制限時間・情報の伏せ方・連続正解は使わない(DESIGN.md 8.18 訂正)。解答の形は知識に合わせて決める: 数値や行番号を読み取る段は入力式、通信を観測する段は模擬ターミナル(`capture` のフィルタ、`show`、`ping`/`tracert`)、再発防止を問う段は RuleEngine の簡略文法で検知ルールを書く。問題はすべて「ログ・キャプチャ生成器」(正常通信を seed から決定的に生成し、既知の異常を注入)で作り、答えは注入記録と独立の検出器の両方で検証してから DB に固定問題として保存する(8.6、8.13)。攻撃の手法名・手順・道具の用法は本文にも解説にも書かず、安全リンタ(`banned.json`)で機械的に弾く。

### 800〜899 複合(攻略と防御)

700〜799 で身につけた「1 つの仕組みを読んで原因を言う」力を、**複数の仕組みが同時に効いている架空ネットワークを通す・守る**力に広げる領域。問題はすべてゲーム内の架空ネットワーク(対象拠点の 10.x.0.0/16 の中に置く 3〜8 拠点の小さな網。拠点名は入口GW・中継DC・支社R・保守SW・おとりDC・目標IX のような架空名、外側のアドレスは文書用範囲)で完結し、現実の攻撃技術・ツール・手順は一切扱わない。攻め手の問いは「与えられた構成とゲーム内のルールを読み解き、目的地へ届く経路と手順を見つける」パズル、守り手の問いは同じ seed の構成を「直す・塞ぐ」問題で、常に対にして同じ重みで出す。難しさを上げる軸は 3 つだけ: **(1) 組み合わさる仕組みの種類と数**(経路表 → +ACL → +NAT → +VLAN → +トラップ → +通行ルール)、**(2) 拠点数**(3 → 8)、**(3) 拠点間の依存**(なし → 片方向 → 往復で経路が違う → 連鎖 → 自分の操作が依存を生む)。制限時間・情報の伏せ・2 問連続は使わない(DESIGN.md 8.18 訂正)。「読解の段数」は、答えに至るまでに評価しなければならない(拠点 × 仕組み)の数で、各段の目安を書く。解答の形は知識に従う: 表と図を読めば決まるものは入力、経路を自分で足す知識なら模擬ターミナルで `route add`、守る側は設定行を直す(コマンドは手で打つ。選ぶボタンは作らない)。通行ルールの「時刻帯」はゲーム内の離散の帯(朝・昼・夜など)を表から読むもので、実時間の制限ではない。

## 5. 自動生成の方式と共通部品

**方針**: 答えの正しさは「ゲーム本体を架空ネットワークの決定的シミュレータにし、サーバーが真のモデルを持って答えを計算する」ことで保証する。生成物は、生成器とは別の総当たり解法で解き直して検証する(`test/check.js` と同じ思想)。クライアントには答えを送らない。

### 方式の定義

| 方式 | 内容 | 検証 |
|---|---|---|
| 計算生成 | 値を乱数で作り、答えを式で再計算する(サブネット、変換、最長一致など) | 答えを別実装で再計算。境界値をテスト |
| テンプレート+乱数 | FactBank(知識カード表)や固定文型に乱数の値を差し込む | 表の値。誤答が正解と異なることをテスト |
| シナリオ生成器 | 架空グラフとルールを生成 → シミュレータで真実を計算 → 探索器で「解が存在・解の個数が意図どおり・手数と所要が帯の範囲・罠は観測で見抜ける」を確認してから保存 | 独立した総当たり解法で解き直して突き合わせ |
| 固定(AI 下書き + 人確認) | 内容が時とともに変わる概念問題。AI が下書きし人が一度確認した FactBank 項目を描く | 表の値。計算できる部分は計算生成に回す |

- **seed 方式**: 問題 = (テンプレート id, seed, 生成器の版) で保存し、乱数は seed 付き。再現できるので 8.6 の「クリアで差し替え」は seed を変えるだけ。DB には seed に加えて描画済み本文・答え・判定方式のスナップショットも保存する(版が変わっても再現できるように)。
- **解を先に植える(plant-then-perturb)**: 帯 H/I は参照解(手順・構成)を先に作り、周囲を乱数で埋め、探索器は一意性・非自明性(最短手数が下限以上、貪欲法で解けない)・罠性の確認だけに使う。解の存在が構成上保証され検証が軽くなる。
- **生成の実行場所**: 生成・検証は手元/CI のスクリプト(`npm.cmd run questions:gen`)で行い DB へ書く。App Service 上では回さない(CPU と Cosmos の RU を食うため)。

### 方式ごとの件数(旧版の題材一覧での集計。領域ごとの再集計は実装時に行う)

| 方式 | おおよその件数 | 主な帯 |
|---|---|---|
| 計算生成 | 約 19 | A・B・F・運用 |
| テンプレート+乱数 | 約 32 | A・C・D・一部 B/G |
| シナリオ生成器 | 約 66 | C〜I の大半 |
| 固定(AI 下書き + 人確認) | 1 | 2.10「新しい技術の考え方」 |

帯 E 以降で「固定(DB)」としていた供給方式は、「シナリオ生成器で作り、保存前に探索器で検証して DB に置く」に置き換える(人手固定は帯 I の段の並びと FactBank の確認だけ。採用は未決 #10)。

### 共通部品(= 第 6 章の実装項目の中身)

- **FactBank**: 用語・層・ポート・AD 値・DSCP・規格などの知識カード表。テンプレート+乱数の土台。
- **NetGen**: 架空ネットワーク生成器(拠点の 10.x.0.0/16 の中に機器・リンク・VLAN を seed から作る)。
- **シミュレータ**: 最長一致の転送・ACL 評価・NAT・traceroute・VLAN・STP・OSPF(Dijkstra)・BGP ベストパス・DNS 解決。答え・ターミナル出力・設定判定・検知の唯一の真実。
- **探索器(Reach)**: 到達可能性と制約充足を BFS/DFS で解く。保存前検証とプレイ中の状態判定の両方に使う。
- **ログ・キャプチャ生成器**: 正常通信に既知の異常を注入してログ/キャプチャを描く(帯 G の中核)。
- **RuleEngine**: ゲーム内 IDS のルール言語。守る側(ルール作成)と攻め手(ルールを読む)が同じ seed で対になる。実機の構文に機械変換できない簡略文法にする。
- **安全リンタ**: 生成・手作りの本文を、使えるアドレス範囲と禁止語で機械検査する(2.11 末尾の安全面)。

### 安全面(3.5 の機械的な担保)

全部品は架空の範囲だけで動く。外側(インターネット側)に使うアドレスは文書用・試験用の範囲に固定する: `192.0.2.0/24`・`198.51.100.0/24`・`203.0.113.0/24`・`2001:db8::/32`、内側は `10/8`・`172.16/12`・`192.168/16`・`fe80::/10`・`fd00::/8`、AS 番号はプライベート `64512〜65534`。ホスト名はゲーム内専用の実在しない接尾辞に限る。禁止語(実在製品名・マルウェア名・攻撃ツール名・走査系コマンド名)は `banned.json` で弾く。検査対象は本文だけでなく、解説・守り側の注記・NPC の命令列・通知文・ターミナル出力書式・トラップ説明・下書きも含める。攻め手の題材は探索器が「構成を読んだ結果の経路」を答えにするだけで、本物に使える手順は生成されない。守り側の解説(defenseNote)が空でないことも検査し、攻守同重を保つ。
